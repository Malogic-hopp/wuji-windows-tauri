# WUJI（吾迹）App UI 与产品逻辑重构方案

> **文档类型**：产品设计、信息架构与 UI 重构方案
> **适用范围**：WUJI Windows WPF 桌面端
> **方案版本**：综合修订版
> **核心主线**：**自动记录 → 还原一天 → 识别工作主线 → 发现行为模式 → 改善下一天**

---

## 1. 项目背景

WUJI 是一款本地优先的 Windows 活动追踪工具。后台 Agent 自动采集前台应用和窗口活动，将原始采样聚合为 Session，并进一步生成应用统计、工作块、任务切换与每日洞察。所有数据保存在用户本机，无需账号，也不依赖网络；App 与 Agent 独立运行，即使主界面关闭，后台仍可持续记录。

当前系统已经具备较完整的工程能力：

* WPF App 与 Agent 双进程；
* Named Pipe IPC 与文件系统 fallback；
* SQLite 本地数据库；
* 前台窗口采样与隐私过滤；
* Session 自动聚合；
* Dashboard、Apps、Sessions、Samples、Insights、Diagnostics 和 Settings；
* 系统托盘、开机自启与后台运行。

现有架构可以继续保留。本轮重构重点不是重写采集系统，而是重新组织产品逻辑、页面关系和用户交互，使 WUJI 从“活动采集与诊断工具”转变为真正的“个人时间回顾与工作节奏改善产品”。

---

# 2. 产品定位

## 2.1 新产品定义

WUJI 应定位为：

> **一款本地运行的个人时间回顾与工作节奏改善工具。它自动记录用户在电脑上的活动，将零散的应用操作整理为时间线、工作上下文、活动热力图和行为洞察，帮助用户看清一天去了哪里，并逐步改善工作方式。**

WUJI 不应首先表现为：

* Agent 服务控制台；
* Sample 原始数据浏览器；
* Session 数据表；
* SQLite、IPC 和状态文件诊断工具。

这些能力仍然保留，但应进入高级层级。

---

## 2.2 产品需要回答的核心问题

1. **今天的时间去了哪里？**
2. **今天主要在推进哪些工作？**
3. **哪些应用切换属于正常工具协作，哪些是真正的任务切换？**
4. **什么时候工作最稳定，什么时候最容易被打断？**
5. **最近一周或一个月的节奏发生了什么变化？**
6. **下一步最值得调整的行为是什么？**

---

# 3. 最关键的产品认知

## 3.1 应用不是任务

对于开发、研究和写作工作，用户经常需要在多个工具之间切换。

例如一段正常的开发流程可能是：

```text
Code
→ Codex
→ Edge 文档
→ Windows Terminal
→ Obsidian 记录
→ Code
```

这些应用虽然不同，但可能始终围绕同一个目标：

> 开发 WUJI 的时间线页面。

因此：

> **应用切换频繁，不等于任务切换频繁，更不等于工作不专注。**

WUJI 不应以单个应用作为任务单位，也不应直接使用应用切换次数判断工作是否碎片化。

---

## 3.2 分析对象应从“应用”升级到“工作上下文”

建议形成四层数据理解模型：

```text
原始采样 Sample
       ↓
应用会话 App Session
       ↓
活动上下文 Context Segment
       ↓
工作块 Work Block
```

### 原始采样

记录某个采样时刻：

* 前台应用；
* 窗口标题；
* 时间；
* Active、Idle 或 Unknown。

### 应用会话

表示连续使用某个应用或窗口的时间：

```text
14:05–14:08  Code
14:08–14:10  Edge
14:10–14:12  Windows Terminal
```

### 活动上下文

把应用和窗口映射为实际活动：

```text
Code                  → 开发
Codex                 → 开发
Windows Terminal      → 开发
Edge 开发文档         → 开发
Edge 论文页面         → 研究
Obsidian 方案文档     → 开发 / 写作
微信                  → 沟通
```

### 工作块

将围绕同一目标持续发生的活动聚合起来：

```text
14:05–15:34
WUJI 功能开发

持续时间：89 分钟
使用工具：Code、Codex、Edge、Terminal、Obsidian
工具跳转：69 次
上下文切换：4 次
沟通中断：3 次，共 6 分钟
```

工作块才是用户真正能够理解的分析单位。

# 4. 核心术语与指标体系

为避免把正常工具协作误判为碎片化，WUJI 应明确区分以下概念。

## 4.1 工具跳转

定义：

> 前台应用或窗口发生变化。

例如：

```text
Code → Edge
```

工具跳转反映工作流复杂程度，但不直接代表负面行为。

---

## 4.2 上下文切换

定义：

> 用户从一种活动上下文进入另一种活动上下文。

例如：

```text
开发 → 沟通
研究 → 开发
写作 → 娱乐
```

上下文切换比应用切换更接近真实的任务变化。

---

## 4.3 外部中断

典型序列：

```text
开发 → 微信 → 开发
```

当中间活动持续时间较短，并且用户快速回到原工作上下文时，应识别为：

> 一次沟通中断。

而不是拆成两次完整的任务切换。

---

## 4.4 有效任务切换

定义：

> 用户持续进入另一个工作目标，并且没有立即返回原目标。

判断依据包括：

* 前后活动类别；
* 新活动持续时间；
* 是否返回原上下文；
* 窗口标题；
* 前后行为序列；
* 用户自定义规则。

---

## 4.5 稳定工作

建议在核心 UI 中使用“稳定工作”，弱化容易过度解释的“专注度”。

定义：

> 一段时间内，用户虽然可能使用多个工具，但活动始终围绕同一工作上下文展开，并且无关中断占比较低。

稳定工作不要求始终停留在同一个应用。

---

## 4.6 核心指标

首页建议使用：

| 指标    | 含义               |
| ----- | ---------------- |
| 有效使用  | 当日 Active 状态累计时间 |
| 稳定工作  | 落在稳定工作块中的有效时间    |
| 上下文切换 | 实际工作上下文发生变化的次数   |
| 最长工作块 | 持续时间最长的工作块       |

详细页面补充：

* 工具跳转；
* 外部中断次数；
* 中断总时长；
* 中断后恢复时间；
* 主要工作上下文；
* 无关活动占比；
* 工作块稳定性。

# 5. 产品设计原则

## 5.1 时间优先

先还原一天发生了什么，再展示抽象统计。

## 5.2 工作主线优先

默认展示“开发、研究、写作、沟通”等上下文，而不是只展示进程名。

## 5.3 工具切换中性化

工具跳转属于描述性指标，不能天然视为负面指标。

## 5.4 结论优先

页面先告诉用户最重要的发现，再提供详细数据。

## 5.5 行动优先

重要洞察应包含明确、可执行的改进建议。

## 5.6 渐进式披露

普通用户先看到时间、工作块和健康状态；PID、IPC、Tick 和 JSON 状态放入高级诊断。

## 5.7 隐私可见

“数据只保存在本机”需要成为界面中的常驻信任信息。

## 5.8 可解释

每个“稳定”“碎片化”“中断较多”的结论，都应说明判断依据。

## 6.2 页面职责

| ----- | ----------- | --------------------------- |
| 今天    | 今天整体怎么样     | 核心指标、今日时间线、今日结论、活动热力图、关键工作块 |

## 7.1 顶部页面栏

顶部只展示：

* 当前页面；
* 日期或时间范围；
* 页面筛选；
* 简化 Agent 状态；
* 当前页面的主要操作。

不再长期展示完整的 Start、Stop、Pause、Resume、Refresh 按钮组。

# 8. Agent 状态与控制

## 8.1 默认状态

顶部只显示：

```text

```

副状态：

```text
3 秒前完成记录
```

点击展开：

```text
正在记录

最近记录：3 秒前
数据仅保存在本机

[暂停记录]
[查看运行状态]
[更多操作]
```

---

## 8.2 状态与主操作

| 当前状态 | 主操作   |
| ---- | ----- |
| 未运行  | 开始记录  |
| 正在记录 | 暂停记录  |
| 已暂停  | 恢复记录  |
| 状态异常 | 检查并修复 |
| 维护中  | 查看进度  |

“停止 Agent”放入：

```text
状态菜单 → 更多操作 → 停止后台服务
```

---

## 8.3 暂停记录

提供更符合实际场景的选项：

* 暂停 15 分钟；
* 暂停 1 小时；
* 暂停到明天；
* 暂停直到手动恢复。

暂停期间明确显示：

> 记录已暂停，本时间段不会保存应用活动。

* 今天记录了多久；

* 是否形成稳定工作；
* 是否存在明显中断；

## 9.3 今日时间线概览

首页默认展示“工作上下文”，而不是每一个应用：

```text

写作
沟通
浏览
娱乐
其他

```

应用明细在点击工作块后展开。

---

## 9.4 今日结论

首页只展示一条优先级最高的洞察。

推荐示例：

> **今天的工作主线整体稳定。**
> 虽然 Code、Codex、Edge 和终端之间发生了较多工具跳转，但这些活动大部分属于同一开发流程。真正跨工作上下文的切换为 12 次，微信造成了 3 次短时中断。
> 下一段工作可尝试关闭微信提醒，减少开发工作块内部的外部中断。

避免出现：

> 今天切换了 370 次，工作非常碎片化。

# 10. 活动热力图设计

热力图明确保留，并成为 WUJI 的核心可视化之一。

## 10.1 热力图职责

热力图回答：

* 通常在什么时候使用电脑；
* 哪些时段更容易形成稳定工作；
* 哪些时段中断较多；
* 最近是否存在熬夜或节奏漂移；
* 今天与过去几天是否明显不同。

---

## 10.2 首页轻量版

首页展示：

```text
最近 7 天 × 24 小时
```

每格代表 1 小时。

默认指标：

> 有效使用时长。

颜色等级建议：

|     有效使用 | 显示等级  |
| -------: | ----- |
|     0 分钟 | 无色或浅灰 |
|  1–15 分钟 | 一级    |
| 16–30 分钟 | 二级    |
| 31–45 分钟 | 三级    |
| 46–60 分钟 | 四级    |

颜色深只表示活动时间更多，不能直接解释为更专注。

---

## 10.3 趋势页完整版

支持范围：

```text
最近 7 天
最近 30 天
最近 12 周
```

支持指标：

```text
有效使用
稳定工作
上下文切换
外部中断
```

其中：

* **有效使用**：Active 时间；
* **稳定工作**：处于稳定工作块中的时间；
* **上下文切换**：跨活动上下文的切换次数；
* **外部中断**：短暂离开原工作主线的次数或总时长。

工具跳转可以作为高级分析选项，但不建议作为默认热力图指标。

---

## 10.4 Tooltip

鼠标悬停显示：

```text
7月11日 14:00–15:00

有效使用：43分钟
稳定工作：31分钟
工具跳转：28次
上下文切换：3次
外部中断：1次，共2分钟
主要活动：开发
主要工具：Code、Edge、Codex
```

---

## 10.5 点击联动

点击热力格后：

1. 跳转到时间线；
2. 自动选择对应日期；
3. 自动定位到对应小时；
4. 高亮该时间段；
5. 展示该小时的工作上下文和应用明细。

---

## 10.6 数据来源

热力图应优先基于：

```text
Context Segment
Work Block
App Session
```

而不是直接使用原始 Samples 数量。

这样可以避免：

* 采样间隔变化导致颜色失真；
* 同一应用频繁采样导致视觉夸大；
* 把工具跳转错误解释为不稳定。

---

# 11. “时间线”页面

时间线是 WUJI 的核心页面。

## 11.1 双层时间线

### 默认层：工作上下文时间线

```text
14:00 ─────────────────────────────────────────────── 18:00

开发       ████████████████████████
沟通              ▏    ▏       ██
研究                          █████
娱乐                                ██
```

这一层帮助用户理解：

> 这一段时间主要在做什么。

---

### 详细层：应用活动时间线

点击某个工作块后，展示应用明细：

```text
Code              ███ ▏███  ▏████
Codex               ██   ▏██
Edge               ▏██ ▏███
Windows Terminal        ▏█ ▏
Obsidian                     ██
微信                   ▏       ▏
```

这一层可以保留用户当前已经生成的应用时间线能力，用于查看多工具协作和中断细节。

---

## 11.2 页面结构

```text
时间线                                      2026年7月12日

[工作上下文] [应用明细] [会话列表]          [类别筛选 ▾]

00:00 ─────────────────────────────────────────────── 24:00
```

顶部筛选：

* 全部；
* 开发；
* 研究；
* 写作；
* 沟通；
* 浏览；
* 娱乐；
* 其他。

# 12. 工作块识别逻辑

初期建议采用可解释的规则系统。

## 12.1 同类工具切换不拆分

```text
Code → Codex → Terminal → Edge 文档 → Code
```

当这些活动被映射到“开发”时，应维持同一个开发工作块。

---

## 12.2 短时离开后返回，识别为中断

```text
开发 20分钟
微信 1分钟
开发 15分钟
```

聚合为：

```text
开发工作块 36分钟
其中包含1次微信中断，共1分钟
```

---

## 12.3 持续进入新上下文才结束工作块

```text
开发 30分钟
微信 12分钟
娱乐浏览 18分钟
```

原开发工作块结束，并进入新的活动块。

---

## 12.4 空闲时间超过阈值时结束

建议区分三个阈值：

| 阈值      |      示例 | 用途            |
| ------- | ------: | ------------- |
| 活动空闲阈值  |    60 秒 | 判断当前采样是否 Idle |
| 短时中断阈值  |  2–3 分钟 | 判断是否保留原工作块    |
| 工作块断开阈值 | 5–10 分钟 | 判断工作块是否结束     |

实际数值应通过真实数据验证，并允许在高级设置中调整。

# 23. 验收标准

## 23.1 产品逻辑

* 不以单个应用作为任务单位；
* 不以工具跳转次数直接判断碎片化；
* 工具跳转、上下文切换和外部中断分别统计；
* 工作块允许包含多个应用；
* 所有稳定性判断都有解释依据。

## 23.2 首页

* 核心指标不超过四项；
* 明确保留活动热力图；
* 只展示一条主要洞察；
* 不展示 PID、IPC 和 SQLite；
* 今日结论能够区分正常多工具协作与真实中断。

## 23.3 时间线

* 默认展示工作上下文；
* 支持展开应用明细；
* 支持按日期、类别和应用筛选；
* 点击工作块可查看详细统计；
* 原始采样记录仍然可访问。

## 23.4 热力图

* 有效使用、稳定工作和上下文切换不混淆；
* 有明确图例和 Tooltip；
* 支持点击定位时间线；
* 使用聚合时长而非 Samples 数着色；
* 30 天范围加载流畅。

## 23.5 洞察

* 每条结论包含数据证据；
* 有足够历史数据时提供个人历史对比；
* 数据不足时不输出强判断；
* 建议具体且可执行；
* 不把应用切换直接描述为不专注。

## 23.6 隐私

* 明确说明数据仅保存在本机；
* 可以快速暂停记录；
* 可以管理排除应用与窗口规则；
* 可以导出、清理和清空数据。

## 23.7 稳定性

* UI 重构不影响 Agent 独立运行；
* 关闭主窗口后仍能采集；
* IPC 和文件 fallback 保持可用；
* 原始记录和完整诊断仍然可以访问。

# 25. 方案结论

本轮重构的核心不是减少功能，而是重新定义 WUJI 如何理解用户的电脑活动：

> **应用是工具，工作上下文才是分析单位；工具跳转是工作方式，上下文切换才可能意味着碎片化。**

最终产品应形成以下主线：

> **通过时间线还原一天，通过热力图发现节奏，通过工作块识别主线，通过洞察解释问题，通过趋势验证改善。**

其中：

* 时间线负责“发生了什么”；
* 应用明细负责“使用了哪些工具”；
* 工作块负责“围绕什么目标工作”；
* 热力图负责“长期节奏如何分布”；
* 洞察负责“哪些行为值得关注”；
* 趋势负责“调整是否真正有效”。

这样既能保留 WUJI 当前完整的采集、统计和诊断能力，也能正确理解 Code、Codex、Edge、Terminal、Obsidian 等多工具协作场景，避免把正常的高强度工作误判为频繁任务切换。
