# WUJI v2 第二轮设计审核回应

审核对象：第一轮修订后的重构文档集
回应日期：2026-07-18
审核入口：[README.md](./README.md)

## 1. 结论

第二轮审核判断成立，尤其是五个 P0 都指向同一根因：把“算法世代”“查询发布”“历史覆盖范围”压在一个可推进 Generation/Snapshot 上，无法同时满足长期历史、未来设置生效和稳定读取。本轮已改为：

```text
Capture Sequence（Runtime 内）
        ↓ Writer 分配
Fact Cursor（数据库全局）
        ↓ staging
Segmentation / Work / Analysis Generation（算法谱系）
        ↓ seal
Result Set Components（不可变 Segmentation/Work/Analysis/Projection 发布单元）
        ↓ non-overlapping coverage
Query Snapshot Slice[]（不可变查询清单）
```

“已修复”仍表示设计合同闭合，不表示代码完成。文档继续保持 Draft/Proposed；正式 DDL 仍被机器可读 manifest 门禁阻断。

## 2. P0：阻断实施问题

| 问题 | 处理 | 回应与落点 |
|---|---|---|
| P0-1 旧历史与单一 Snapshot 无法共存 | 已修复 | Snapshot 改为多个不重叠 Slice 的不可变清单；每个 Slice 分别引用可复用的 Segmentation/Work/Analysis/Projection Result Set 组件。最近范围可用新算法，旧原生 v2 使用 `NativeV2Summary`，v1 才使用 Legacy。见[Result Set 与 Snapshot Slice](./02-行为分析领域模型.md#126-result-set)和[持久化结构](./04-SQLite-v2与持久化读模型.md#510-result_sets)。 |
| P0-2 Settings Revision 与 Advancing Generation 冲突 | 已修复 | 完整 Settings Revision、每条事实的 Capture Revision、Segmentation/Work/Analysis Profile 和 Effectivity Interval 分离。未来-only 变化只切 Effectivity；Profile 未变时 Generation 继续推进。见[Settings Effectivity](./02-行为分析领域模型.md#125-settings-effectivity)和[Profiles](./04-SQLite-v2与持久化读模型.md#54-profiles-与-settings_effectivity_intervals)。 |
| P0-3 Capture Sequence 水位缺 Runtime 维度 | 已修复 | Capture Sequence 明确为 Runtime-local；Writer 在事务中分配数据库全局 Fact Cursor，所有跨重启水位改用 Fact Cursor。见[时间值对象](./02-行为分析领域模型.md#31-时间)和[`database_metadata`](./04-SQLite-v2与持久化读模型.md#52-database_metadata)。 |
| P0-4 Snapshot 不是稳定读取快照 | 已修复 | Advancing Generation 只写 staging；Sealed Result Set 永不更新。语义查询在同一 SQLite read transaction 解析 Snapshot/Slice 并读数据，分页用 lease 固定同一逻辑发布。Calendar 追平由 Result Set Fact Cursor 证明。见[稳定读取](./04-SQLite-v2与持久化读模型.md#13-历史重建与原子切换)。 |
| P0-5 Start/Stop 的进程与采集语义混合 | 已修复 | 拆为本地 `StartAgentProcess/EnsureAgentProcess`、IPC `CaptureStart/Stop` 和 `ShutdownAgent`。退出前持久化终态 receipt；Pipe 消失后由只读 Storage Query 查询并结合 process handle 确认。见[进程控制与采集控制](./06-本地接口与错误合同.md#7-进程控制与采集控制)。 |

## 3. P1：重要设计问题

| 问题 | 处理 | 回应与落点 |
|---|---|---|
| P1-1 Work 生命周期仍耦合 Context Generation | 已修复 | 新增独立 Work Generation/Work Profile；Work Block 不再含 Analysis Generation ID，Context alias/classifier 变化不创建 Work Generation。见[Work Generation](./02-行为分析领域模型.md#123-work-generation)和[`work_blocks`](./04-SQLite-v2与持久化读模型.md#78-work_blocks)。 |
| P1-2 Return Window 参数实际无效 | 已修复 | 第一版删除独立 `interruption_return_window`；返回发生在 Context commit 前才是 Interruption，commit 后返回是两次 Switch。未来如需撤销已提交 Switch，必须另建 provisional 生命周期。见[Interruption](./01-产品语义与指标词典.md#312-interruption)。 |
| P1-3 “理论可采集时长”未定义 | 已修复 | 改为 Tracking Expectation Interval；只让 Expected 进入分母，主动暂停/停止、计划外、独占维护和系统不可用不惩罚用户，意外离线计 AgentUnavailable。见[质量口径](./01-产品语义与指标词典.md#63-数据质量指标)和[Expectation 实体](./02-行为分析领域模型.md#44-tracking-expectation-interval)。 |
| P1-4 长期事件解释能力不足 | 已修复 | 新增 Decision Evidence Snapshot 与 `FullEvidence/DecisionSummary/MetricOnly` 能力。90 天后可降级但仍保留规则 ID、版本、边界摘要、reason/confidence。见[解释能力](./01-产品语义与指标词典.md#7-数据可重建等级)和[`decision_evidence_snapshots`](./04-SQLite-v2与持久化读模型.md#77-decision_evidence_snapshots)。 |
| P1-5 逻辑 Schema 不足以直接生成 manifest | 部分修复，保留门禁 | 查询关键表已逐列展开，拆开 Event 表并列出 composite FK/PK/index/check；但 Markdown 明确不再冒充机器输入。正式 DDL 前必须提交 `schema-v2-manifest.yaml`，在此之前 drift gate 不得标为通过。见[机器 manifest 门禁](./04-SQLite-v2与持久化读模型.md#162-机器可映射-manifest-门禁)。 |
| P1-6 Superseded Snapshot 无回收策略 | 已修复 | 新增 Snapshot Lease、过期、最小回滚集合、Collectable 状态和 Result Set/Generation 分层 GC。Desktop 崩溃靠 lease TTL 释放。见[Snapshot lease 与 GC](./04-SQLite-v2与持久化读模型.md#121-snapshot-lease-与-gc)。 |
| P1-7 Clear Receipt 范围冲突 | 已修复 | 删除“导出 receipt”遗留措辞；Clear 不删除 `command_receipts`，当前及未过期 receipt 由独立 TTL 清理。首版明确没有 export receipt 表。见[Clear 范围](./04-SQLite-v2与持久化读模型.md#12-保留与清理)。 |
| P1-8 Identity Generation 未持久化 | 已修复 | 新增 `identity_generations`、`identity_links`，App Identity 绑定世代；只允许可信运行时连续性或用户确认建立跨世代链接。见[Identity Generation](./04-SQLite-v2与持久化读模型.md#61-identity_generations-与-identity_links)。 |
