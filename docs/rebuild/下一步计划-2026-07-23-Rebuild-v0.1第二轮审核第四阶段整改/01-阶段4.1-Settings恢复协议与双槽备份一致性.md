# 阶段 4.1：Settings 恢复协议与双槽备份一致性

## 阶段目标

关闭审核 P1-01：让 SQLite revision/digest metadata、settings 文件和双槽完整内容
组成可证明的 crash-consistent 恢复协议，彻底禁止静默回退 revision 0 或默认排除名单。

本阶段只修 Settings 持久化、启动对账和相关测试，不实施 Coordinator、Barrier、
effectivity 或 Lock/Sleep。

## 必须实现

1. 启动时读取 `Writer::latest_settings_revision_digest()`。
2. 对账同时考虑 DB metadata、settings 文件、双槽候选。
3. DB revision > 0 时，只有与 DB revision/digest 匹配的完整内容，或合法严格前滚文件可用。
4. 无法恢复 DB 当前 revision 时：
   - `capture_allowed=false`；
   - 不回默认值；
   - IPC 保持在线；
   - 上报来源明确的安全错误。
5. Settings 应用和双槽备份采用 crash-consistent 顺序。备份失败不得无条件返回成功。
6. 双槽读取不能只按“最高 revision”信任，必须与 DB metadata 交叉验证。

## 必测场景

- 全新 DB revision 0，无文件/备份；
- DB=N，文件与 DB 匹配；
- DB=N，备份与 DB 匹配、文件损坏；
- 文件 N+1 合法前滚；
- 文件/备份 revision 低于 DB；
- 同 revision digest 冲突；
- DB>0 且文件/双槽均不可恢复；
- 备份写失败；
- DB commit 前/后故障；
- 高 revision 候选存在但 DB 未提交时不得误应用。

## 验收标准

- `unrecoverable_last_known_good_blocks_capture` 名称与断言一致；
- excludedProcessNames 不会因恢复失败被清空；
- DB、backup、SharedState 的 revision 语义一致；
- 本阶段相关测试不依赖真实旧数据库；
- Rust fmt/check、Agent lib、storage 测试通过。

## 明确不做

- 不接入 CaptureCoordinator；
- 不改变 Barrier 拓扑；
- 不做 Settings effectivity；
- 不做 Lock/Sleep；
- 不更新 migration-status 为完成；
- 不运行 package 或 soak。
