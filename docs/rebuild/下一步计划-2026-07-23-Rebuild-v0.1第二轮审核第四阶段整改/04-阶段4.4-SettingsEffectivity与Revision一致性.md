# 阶段 4.4：Settings effectivity 与 revision 一致性

状态：**Ready，允许开始实施**（2026-07-27；4.3.1 已复审通过）。  
实施前必须阅读
[阶段4.4-启动准备-2026-07-27.md](./阶段4.4-启动准备-2026-07-27.md)；该文件中的
当前代码缺口、推荐失败语义和 E01–E12 测试矩阵属于本阶段验收条件。

## 阶段目标

关闭 P1-04：Settings 切换边界前后，Capture、Processor、Writer、ActivityEngine 和
SQLite 使用同一 revision 与同一 Settings 语义。

## 固定执行顺序

```text
获取 transition lock
→ 冻结 effective capture
→ 注入 Barrier 并等待 injected ack
→ Writer 排空到 Barrier
→ 提交新 Settings
→ 更新 SharedState applied revision
→ 发布 Settings watch
→ 确认发布完成
→ 按 desired/suppression 恢复 effective capture
```

## 必须实现

1. Barrier 前 Sample 全按旧 Settings/旧 revision。
2. Barrier 后不得产生旧 revision Sample。
3. Processor revision 不匹配时显式失败，不得继续用当前 Settings。
4. Observation、PrivacyExcluded、CaptureError 全部校验 revision。
5. excludedProcessNames、idle threshold、work threshold 遵守同一边界。
6. Settings commit 失败时 DB、engine、watch、SharedState、DTO 保持 last-known-good。
7. 不允许静默丢 Observation 或把旧消息重标新 revision。
8. revision mismatch 属于流水线协议错误：不得继续使用当前 Settings；必须留下
   `SETTINGS_CONFLICT` 证据并 fail-closed，IPC/Diagnostics 保持在线。
9. Writer 对 Observation、PrivacyExcluded、CaptureError 使用同一 revision 防线。
10. 不得回退 4.3.1 已建立的 control-send deadline、unknown fencing、pipeline
    supervisor 或 RequestIdCache Active/Completed 语义。

## 必测场景

- revision 0→1；
- Barrier 前/后 Observation revision；
- excludedProcessNames 开启和移除；
- idle threshold 改变；
- work threshold 改变；
- PrivacyExcluded/CaptureError revision 错配；
- watch 发布失败或接收方退出；
- Settings commit 失败后的重试。
- 三类 ProcessorOutput 的 Processor/Writer 双层 revision mismatch；
- IPC reload 与 reconciler 的真实并发重叠；
- DB/Engine/SharedState/watch/DTO 五方一致性。

## 验收标准

- Processor 中不存在“错配仍继续处理”；
- 所有数据变体均有 revision 防线；
- 测试通过真实 Coordinator + Capture FIFO；
- 规则切换测试必须使用真实 Processor + Writer + 临时 SQLite，不能只手工注入
  `ProcessorOutput` 代替端到端证据；
- fmt/check/clippy 和 Settings lifecycle 专项测试通过。

## 明确不做

- 不完成 Lock/Sleep 状态叠加；
- 不运行 8 小时 soak；
- 不把历史证据标成当前证据。
