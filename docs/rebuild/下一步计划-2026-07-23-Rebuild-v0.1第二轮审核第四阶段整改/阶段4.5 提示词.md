## 必须采用的方案

1. 定义平台无关的四态 Agent 输入（Lock/Unlock/Sleep/Resume），Windows adapter
   不得直接操作 Coordinator 内部状态。
2. Lock 与 Sleep 分别保存 `active + 首次事件时间 + boundary_committed` 等价状态。
   首次进入必须先激活 suppression 并发布冻结，再执行 Barrier→Writer control→ack。
3. 明确未提交失败时保持 suppression 和首次时间；重复同类进入事件必须可重试且最终
   恰好提交一次。ack unknown 沿用 writer_fault，不得重试。
4. 已 active+committed 的重复 Lock/Sleep 幂等，不重复 gap/event_count。Unlock/Resume
   只清自己的 suppression，不创建反向数据库边界，不修改 desired。
5. Lock+Sleep 重叠时，解除一个来源不得恢复采集；最后一个 suppression 解除后，只有
   desired Running、无 fatal/monitor fault 且 PipelineHealth 可发布时才恢复。
6. Lock/Sleep 都使用可靠 Barrier 和 Coordinator 锁内读取的当前 applied revision；
   Settings/Lifecycle/SystemEvent 继续共享唯一 transition lock。
7. 事件泵启动、桥接或运行中异常退出必须进入 `ErrorSource::LifecyclePump` 诊断，并锁存
   不可由普通 Start/Resume 清除的 monitor fault；正常 shutdown 不得误报。
8. 修复 Windows 电源事件接收：默认把 `HWND_MESSAGE` 改成 parent=null、无
   `WS_VISIBLE` 的隐藏顶层窗口，保留 WTS 注册与专用消息循环。若采用受支持的替代
   suspend/resume API，完成说明必须给出 API 生命周期和失败闭环；生产中只能有一条
   电源事件路径。
9. 抽取生产与测试共用的单一 session/power consumer。bounded bridge 遇背压必须保序
   阻塞或显式失败，禁止 `try_send` 后静默丢事件。
10. 严格遵守启动准备文档的失败表和重叠 gap 语义：release 不重写 gap kind；全部
    suppression 解除后的第一条有效 Observation 才关闭最后一个 open gap。

不得只把两个预留 bool 置位就结束；必须能表达并测试“已经安全冻结，但进入边界尚未
提交、等待重复事件重试”的状态。
