# 阶段 4.1 完成说明：Settings 恢复协议与双槽备份一致性

日期：2026-07-23（含复审补修）
阶段目标：关闭审核 P1-01（Settings last-known-good 丢失时静默回退 revision 0）
状态：**阶段 4.1 完成（含复审补修），等待复审**（未开始 4.2）

## 1. P1-01 根因

整改前存在三条互相叠加的错误路径：

1. `main.rs` 启动对账只输入 settings 文件与双槽备份，从未调用已有的
   `Writer::latest_settings_revision_digest()`，DB 已提交的 revision/digest 完全不在
   恢复决策中；
2. `reconcile_startup_settings()` 把 `backed_up == None` 直接转换为 `Settings::default()`，
   DB 已提交 revision N>0 而文件/备份均不可用时，Agent 以 revision 0 默认值继续运行，
   `capture_allowed=true`，默认排除名单生效，SharedState applied revision 被重置为 0；
3. SettingsApplied 先提交 SQLite 再写双槽备份，备份失败仅 `eprintln`，ack 仍返回成功。

另外，双槽恢复只按"最高 revision"信任，无法区分"DB 已提交"与"commit 前崩溃残留"
的槽位；`unrecoverable_last_known_good_blocks_capture` 测试断言与名称相反。

## 2. 复审补修（2026-07-23 复审报告）

复审在初版上发现 3 个 P1 与 1 个 P2，修复如下。

### 复审 P1-01：启动前滚绕过"备份先于 DB"协议

- 新增 `settings_persist.rs`：`apply_settings_persistent()` 是启动前滚、启动幂等恢复与
  运行时 SettingsApplied 的唯一持久化路径（无副作用预校验 → DB 感知候选写入 →
  SQLite 提交 → 幂等路径修复缺失冗余）。
- `main.rs` 启动前滚与 `writer_task` SettingsApplied 均改为调用该函数。
- 幂等路径（内容与 DB 匹配但备份缺失）补建备份冗余；失败返回
  `SETTINGS_SAVED_NOT_APPLIED`，不声称冗余已建立。
- 测试：`settings_recovery::idempotent_apply_repairs_missing_backup`、
  `forward_apply_advances_db_and_backup_together`、真实启动编排 e2e
  `startup_forward_roll_persists_backup_and_repairs_missing_redundancy`
  （三次真实进程重启：前滚持久化 → 备份删除后前滚 → 备份删除后幂等修复）。

### 复审 P1-02：重复失败/无效请求可覆盖两个已提交备份槽

- `write_backup` 改为 DB 感知：槽位选择只由"槽位内容 vs DB metadata"决定——
  恰好一个槽匹配 DB 时写另一个（绝不覆盖唯一 LKG）；两个都匹配写 A；
  都不匹配覆盖 revision 较低的槽。
- 预校验前置：revision 降级与 digest 冲突在触碰任何槽位之前拒绝
  （`apply_settings_persistent` 先读 `latest_settings_revision_digest` 比对）。
- 测试：`settings_recovery::consecutive_db_commit_failures_preserve_db_matching_lkg`
  （写锁强制连续两次 DB commit 失败，唯一 LKG 完好，解锁后同一请求成功）、
  `consecutive_downgrades_do_not_touch_slots`、
  `consecutive_digest_conflicts_do_not_touch_slots`、
  `settings_backup::write_never_overwrites_only_db_matching_slot`。

### 复审 P1-03：marker 更新失败被静默忽略

- marker 机制整体移除（`ACTIVE_MARKER` 读取/写入全部删除）：槽位选择不再依赖任何
  额外状态，安全性只由槽位内容与 DB metadata 决定。磁盘上遗留的旧 marker 文件不再
  被读取，无害。

### 复审 P2-01：Settings 错误覆盖其他来源，成功后不清理

- `main.rs` 启动对账诊断、`writer_task` SettingsApplied 失败均改为
  `shared.set_error(ErrorSource::Settings, code)`；成功应用后
  `shared.clear_error(ErrorSource::Settings)`。
- 不再调用会清空全部来源并归入 Writer 的 `set_safe_error`（Settings 路径）。
- 测试：`shared::tests::errors_are_scoped_by_source`、
  `settings_recovery_clears_only_settings_source`、集成测试
  `settings_lifecycle::successful_apply_clears_settings_error_source_only`
  （Checkpoint 来源全程不受影响）。

## 3. 恢复决策表（`settings_store::reconcile_startup_settings`）

输入：DB 最大已应用 `(revision, digest)`、settings 文件（`SettingsLoad`）、经 DB
metadata 交叉验证的双槽候选（`read_backup_matching` 已过滤）。

| 场景 | 决策 | capture_allowed | diagnostic | applied_revision |
|---|---|---|---|---|
| DB=0，文件缺失 | revision 0 内建默认 | true | None | 0 |
| DB=0，文件损坏 | revision 0 内建默认 | true | SETTINGS_INVALID | 0 |
| DB=N>0，文件与 DB 匹配 | 使用文件 | true | None | N |
| DB=N>0，文件缺失/损坏，备份匹配 | 从备份恢复（排除名单保留） | true | SETTINGS_INVALID | N |
| DB=N>0，文件缺失/损坏，备份缺失/不匹配 | **阻止** | false | SETTINGS_INVALID | N（不重置为 0） |
| 文件 revision > DB | 合法严格前滚（唯一前滚来源是文件） | true | None | 文件 revision |
| 文件 revision < DB（降级） | 拒绝文件；备份匹配则恢复，否则**阻止** | true/false | SETTINGS_CONFLICT | N |
| 文件 revision = DB 且 digest 冲突 | 拒绝文件；备份匹配则恢复，否则**阻止** | true/false | SETTINGS_CONFLICT | N |
| DB=0 但存在高 revision 备份（未提交） | 忽略备份，revision 0 默认 | true | None | 0 |

## 4. 崩溃窗口处理（统一 crash-consistent 协议）

```text
预校验（降级/digest 冲突在触碰槽位前拒绝）
→ write_backup（DB 感知选槽 + 临时文件 + fsync + 原子 rename）
  → 失败：不提交 DB，返回 SETTINGS_SAVED_NOT_APPLIED，writer 不 faulted（可重试）
→ engine.apply_settings 提交 settings_revisions
```

各窗口行为：

- 写临时文件中途崩溃：只残留 `.tmp`，正式槽位与 DB 均未变；
- 备份完成、DB commit 前崩溃：候选槽含更高 revision，DB 未提交；启动时
  `read_backup_matching` 交叉验证，未提交槽位被忽略；唯一匹配 DB 的 LKG 槽位
  从未被候选覆盖（连续失败也不丢失）；
- DB commit 后崩溃：槽位与 DB 同 revision/digest，正常恢复；
- 备份写失败：DB 不前进、无静默成功。
