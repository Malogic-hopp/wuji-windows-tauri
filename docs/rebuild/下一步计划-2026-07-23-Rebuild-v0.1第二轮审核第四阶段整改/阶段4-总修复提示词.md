## 三、第一批：修复 Settings last-known-good 和启动对账

目标：SQLite 不保存完整 Settings，但 SQLite revision/digest metadata 与双槽完整内容必须组成 crash-consistent 的恢复协议。

必须完成：

1. 在 `main.rs` 打开 Writer 后读取 `Writer::latest_settings_revision_digest()`。
2. 重构 `reconcile_startup_settings()`，至少输入：
   - SQLite 最大已应用 revision/digest；
   - settings 文件加载结果；
   - 双槽备份候选。
3. 明确定义并测试：
   - 全新 DB revision 0 + 无文件/无备份：允许默认 revision 0；
   - DB revision N + 文件 revision N 且 digest 相同：允许；
   - DB revision N + 备份 revision N 且 digest 相同：文件损坏时恢复备份并上报诊断；
   - 文件 revision > DB revision：作为合法 saved-not-applied 前滚候选；
   - 文件或备份低于 DB revision：拒绝降级；
   - 同 revision digest 冲突：拒绝；
   - DB revision > 0 且无法恢复对应完整内容：`capture_allowed=false`，不得回默认值。
4. 修复名为 `unrecoverable_last_known_good_blocks_capture` 的错误测试，使其真正断言阻止 Capture。
5. Settings 应用和双槽备份必须 crash-consistent。推荐方案：
   - 先持久化候选完整 Settings；
   - 再提交 SQLite revision/digest；
   - 启动只信任与 SQLite metadata 匹配的槽位；
   - DB commit 失败时，高 revision 候选槽不得被误当作已应用状态。
   
   可以采用等价设计，但不得在 DB 已前进、备份失败后仍返回无条件成功。
6. 备份失败必须进入来源明确的安全错误，并保持 effective capture 安全冻结或采取同等保守策略。
7. 增加备份写失败、双槽损坏、DB/备份 revision 不一致、commit 前后崩溃点的确定性测试。

## 四、第二批：完成并接入唯一 CaptureCoordinator

目标：Lifecycle、IPC settings_reload、reconciler、Lock/Sleep 只有一个串行化入口。

必须完成：

1. `main.rs` 创建唯一 `Arc<CaptureCoordinator>`。
2. `CommandServerContext` 持有 Coordinator，而不是分别持有：
   - `capture_lock`
   - `control_tx`
   - `capture_state_tx`
   - `barrier_request_tx`
   - `settings_tx`
3. settings reconciler 只调用 `CaptureCoordinator::apply_settings()`。
4. Windows session/power 路径只调用 Coordinator 的 lock/sleep/unlock/resume API。
5. 删除旧的分散控制路径和重复锁。
6. Coordinator 内显式建模：
   - desired/user capture state；
   - session locked suppression；
   - system sleeping suppression；
   - effective capture gate；
   - applied settings revision。
7. effective gate 的计算至少满足：
   - desired=Running 且没有 Lock/Sleep/transition/fault 抑制时才 Running；
   - 用户 Pause/Stop 不因 Unlock/Resume 自动恢复；
   - Lock 与 Sleep 可以叠加，解除一个不能越过另一个；
   - transition 失败保持安全冻结。
8. Start/Pause/Resume/Stop、Settings、reconciler、Lock/Sleep 必须共享同一个 transition lock。
9. IPC 3 秒 timeout 只结束等待，不取消已接受副作用；同 request ID 仍等待原任务结果。

## 五、第三批：实现可靠 BarrierRequest 和 Writer pending

目标：Barrier 不丢失、不超车、不被普通分支吞掉，所有失败都有确定结果。

引入等价于下列结构的请求：

```rust
pub struct BarrierRequest {
    pub token: BarrierToken,
    pub injected_ack: oneshot::Sender<Result<(), SafeError>>,
}
```

必须完成：

1. Capture Loop 仍是 `CapturePipelineItem` FIFO 的唯一生产者。
2. injected ack 只能在 Barrier 成功写入该 FIFO 后返回成功。
3. Barrier 请求 channel Full/Closed、FIFO Closed、Capture Loop/Processor 退出都必须返回稳定失败。
4. 禁止所有 Barrier `try_send` 忽略结果。
5. 一次 transition 只能生成一个 BarrierId；删除 settings_reload 的双 Barrier。
6. Coordinator 收到 injected ack 后再发送对应 WriterControl，或实现等价的无悬挂协议。
7. Writer 普通 data 分支遇到 Barrier 时登记 pending，不得 `return true` 跳过。
8. `pending_barriers` 改为按 BarrierId 索引的有界结构，定义：
   - 最大容量；
   - TTL；
   - 同 ID 同内容重复；
   - 同 ID 不同 kind/revision 冲突；
   - 容量满；
   - Writer shutdown/退出清理。
9. `drain_to_barrier` 按以下三项同时匹配：
   - BarrierId；
   - BarrierKind；
   - expected revision。
10. 注入成功但 control send 失败时，pending token 必须最终过期或取消，不能永久悬挂。
11. control 已登记但 Barrier 失败时，ack 必须返回失败，Writer 不得提交边界。
12. 失败后写入来源明确的 SharedState 安全错误，不得只打印 stderr。

## 六、第四批：修复 Settings effectivity 和 revision 端到端一致性

必须实现以下顺序：

```text
获取统一 transition lock
→ 冻结 effective capture
→ 将 Barrier 注入 Capture FIFO 并等待 injected ack
→ Writer 排空到 Barrier
→ 持久化/应用新 Settings
→ 更新 SharedState applied revision
→ 更新 Processor/Capture 使用的 Settings watch
→ 确认 watch 已发布
→ 按 desired + suppression 恢复 effective capture
```

要求：

1. Barrier 前的 Sample 全部按旧 Settings 和旧 revision 处理。
2. Barrier 后不得产生旧 revision Sample。
3. Processor 不得在 revision 不匹配时继续使用当前 Settings。
4. 对 revision 错配采用显式失败和诊断；不得静默重标或继续处理。
5. 以下所有 ProcessorOutput 数据变体都必须校验 revision：
   - Observation；
   - PrivacyExcluded；
   - CaptureError。
6. ActivityEngine 和 SQLite 最终保存的 revision 必须与 Sample 生效 Settings 一致。
7. Settings 失败时 DB、engine、settings watch、SharedState、DTO 必须保持同一 last-known-good。
8. 增加 revision 0→1、excludedProcessNames、idle threshold、work threshold 切换的边界测试。

## 七、第五批：完成 S2-03 Lock/Sleep

必须完成：

1. Lock/Sleep 通过 Coordinator 设置对应 suppression，并冻结 effective capture。
2. 在真实 FIFO Barrier 后提交 `SessionLocked`/`SystemSleep` 生命周期事务。
3. expected revision 读取当前 applied revision，不得硬编码 0。
4. 等待并处理 Writer ack。
5. Unlock/Resume 只移除对应 suppression。
6. 仅当 desired state 为 Running、无其他 suppression 且 Writer 健康时恢复采集。
7. Pause/Stop 期间的 Lock/Sleep 不改变原有 pause/stop gap 语义。
8. 处理重复、乱序和叠加事件：
   - Lock→Lock；
   - Sleep→Sleep；
   - Lock→Sleep→Resume→Unlock；
   - Sleep→Lock→Unlock→Resume；
   - Pause→Lock→Unlock；
   - Stop→Sleep→Resume。
9. 核实 message-only window 是否能可靠收到真实 Suspend/Resume。如果不能，改用隐藏顶层窗口或 Windows suspend/resume 注册 API。
10. 自动测试只使用可注入事件源验证状态机；真实锁屏/休眠继续标记人工 Pending。

## 八、第六批：补真实拓扑和失败测试

Writer 单元测试可以保留，但必须新增走真实生产组件的测试 harness：

`Coordinator → BarrierRequest → Capture Loop → CapturePipelineItem FIFO → Processor → Writer`

至少覆盖：

1. Capture queue 中多个旧 Sample + Barrier：旧 Sample 全部先于 Barrier。
2. Sample tick 与 Barrier 同时 ready：重复运行不超车。
3. Barrier 在 WriterControl 前到达：进入 pending，不被吞掉。
4. 同 kind 不同 ID：分别匹配。
5. 同 ID 不同 kind/revision：稳定冲突。
6. Barrier request channel Full。
7. Barrier request channel Closed。
8. Capture FIFO Closed。
9. Processor 在 Barrier 前退出。
10. Writer 在等待 Barrier 时退出。
11. Writer 等待 Barrier 超时。
12. in-flight capture 遇到 Pause/Stop/Settings/Lock。
13. Capture queue 满和 drop 后 Barrier 仍可达。
14. Writer queue 满和 drop 后 Barrier 仍可达。
15. Settings revision 0→1 边界。
16. excludedProcessNames 切换边界。
17. idle threshold 与 work threshold 切换边界。
18. PrivacyExcluded/CaptureError revision 错配拒绝。
19. IPC settings_reload 与 reconciler 共用同一 Coordinator。
20. Lock/Sleep 与用户 Pause/Stop 状态叠加。
21. 任一失败后 shared/watch/DTO/SQLite 一致。
22. pending 容量、TTL、重复、冲突和 shutdown 清理。

测试不得依赖随机调度或长时间 `Task.Delay`/sleep。使用 paused Tokio time、oneshot、watch、事件、受控 mock CaptureSource 和确定性 scheduler。

同时修复 `agent_survives_parent_exit_and_offline_read_works_after_kill` flaky：

- 使用确定性的 PID/进程句柄/受控握手定位目标 Agent；
