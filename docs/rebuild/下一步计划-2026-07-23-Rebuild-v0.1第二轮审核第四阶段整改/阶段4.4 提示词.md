## 二、目标与固定时序

关闭 P1-04，让 Capture→Processor→Writer→ActivityEngine→SQLite 在 Settings
边界两侧使用同一 revision 和同一 Settings 语义。

必须保留唯一生产时序：

```text
transition lock
→ freeze effective capture
→ Barrier 写入唯一 CapturePipelineItem FIFO 并收到 injected ack
→ Processor 原样转发 Barrier
→ Writer drain 到 Barrier
→ crash-consistent commit Settings
→ SharedState applied revision
→ Writer ack
→ settings watch 发布
→ PipelineHealth/消费者检查
→ 按 desired/suppression 恢复 effective capture
```

不得增加第二套 settings lock、第二个 Barrier、旁路 WriterControl、直接 watch 更新
路径，也不得削弱 4.3.1 的 control-send deadline、unknown fencing、pipeline
supervisor 与 RequestIdCache 语义。

## 三、必须修复的当前缺口

1. `processor_task.rs` 当前 revision mismatch 仍按“此刻的 settings watch”继续
   处理。必须在业务处理前显式拒绝，不能静默 drop、重标 revision 或继续套用
   当前 Settings。
2. `writer_task.rs` 当前只校验 Observation revision。必须对 Observation、
   PrivacyExcluded、CaptureError 建立统一 revision 防线，再转换 EngineEvent。
3. mismatch 是内部协议不变量破坏：零 ActivityEngine/SQLite 副作用，留下来源明确
   的 `SETTINGS_CONFLICT`，fail-closed，IPC/Diagnostics 在线；后续 start/settings/
   system-event 不得在本进程内绕过 fencing。
4. Barrier 前全部数据保持旧 Settings/旧 revision；Barrier 后首条及以后不得出现
   旧 revision。禁止清队列换绿或把旧消息重标为新 revision。
5. excludedProcessNames 添加/移除、idle threshold、work-break threshold 必须在
   同一 Settings Barrier 上原子切换。
6. commit 明确失败时 DB、ActivityEngine、SharedState applied、settings watch、DTO
   均保持 last-known-good；故障修复后重试恰好提交一次。
7. control accepted 后 ack Closed/timeout/cancel 仍是“结果未知”；DB 已提交但
   watch/最终 publish 失败仍保留已提交事实并安全停止，不能伪装成未提交。

推荐保留现有 Barrier 模型，并为 `ProcessorOutput` 增加统一 revision 访问方法；
Processor mismatch 可使用显式内部错误消息交给 Writer 统一 fatal，或由 Processor
设置诊断后退出并让 supervisor fail-closed。无论选择哪种，都必须证明错误可观察、
零 DB 副作用且没有后续旧 revision 输出。不要无理由扩散到桌面 DTO/bindings。
