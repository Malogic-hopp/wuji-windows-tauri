## 3. 实现细节

### 3.1 G4-01：Processor revision 错配显式拒绝（已闭合）

`processor_task.rs` 在调用 `ObservationProcessor::process()` 前显式比较：

```rust
let sample_rev = raw.settings_revision;
let current_rev = settings.revision.parse::<i64>().unwrap_or(-1);
if sample_rev != current_rev {
    let _ = tx.send(ProcessorOutput::SettingsRevisionMismatch {
        sequence: raw.sequence,
        continuity_epoch: raw.continuity_epoch,
        sample_revision: sample_rev,
        current_revision: current_rev,
    }).await;
    break;
}
```

违例消息与 Barrier 同级可靠阻塞发送，不走 `try_send` 丢弃路径。发送后 Processor 任务退出
（`break`），health guard Drop 触发 pipeline supervisor fail-closed。

### 3.2 G4-02：Writer 统一 revision 防线（已闭合）

`process_data()` 入口处对所有数据变体使用 `settings_revision()` 统一防线：

```rust
if let Some(revision) = message.settings_revision()
    && (self.protocol_violation || revision != self.engine.settings_revision())
{
    self.reject_protocol_violation(message.sequence(), revision);
    return true;
}
```

三类数据变体均被覆盖：
- `Observation(FilteredObservation { settings_revision, .. })`
- `PrivacyExcluded { settings_revision, .. }`
- `CaptureError { settings_revision, .. }`

`reject_protocol_violation()` 只在首次违例时：
- 输出安全诊断（seq/revision，不含进程名）
- `mark_fatal` → Writer/Process Faulted + Capture Stopped
- 留下 `SETTINGS_CONFLICT` 错误
- 本进程内后续数据消息直接拒绝（不再重复刷诊断，与 fenced transition 语义一致）

### 3.3 三类 ProcessorOutput revision 防线对照

| 数据类型 | Processor 防线 | Writer 防线 | 错配行为 |
|---|---|---|---|
| Observation | 业务处理前检查 `raw.settings_revision != current_rev` → 显式违例退出 | `process_data()` 入口处统一 `settings_revision()` 校验 | 零 ActivityEngine/SQLite 副作用；fail-closed；IPC/Diagnostics 在线 |
| PrivacyExcluded | 同上（进程名不得进入业务处理，更不落库） | 同上 | 同上；进程名不得出现在 DB/WAL 字节 |
| CaptureError | 同上（没有进程名可泄露，但仍不得转化为 gap） | 同上 | 同上；不产生任何 gap |

### 3.4 统一 revision 访问方法

`ProcessorOutput::settings_revision() -> Option<i64>`：
- `Observation`、`PrivacyExcluded`、`CaptureError` → `Some(revision)`
- `Barrier`、`SettingsRevisionMismatch` → `None`（不参与数据 revision 防线）

## 5. 失败闭环

### 5.1 revision mismatch 失败语义

```text
Processor/Wrtier 检测到 revision 错配
    ↓
留下 SETTINGS_CONFLICT 诊断（仅 seq/revision，不含进程名隐私内容）
    ↓
mark_fatal：Writer -> Faulted、Process -> Faulted、Capture -> Stopped
    ↓
pipeline supervisor 经同一 transition lock 兜底 fail-closed
    ↓
IPC/Diagnostics 在线
    ↓
本进程内后续 start/settings/system-event 全部被 fencing（AGENT_WRITER_FAULTED）
    ↓
需要 Agent 重启 + 成功启动恢复才重建健康状态
```

### 5.2 commit failure 失败语义

```text
crash-consistent 协议在 DB 提交前失败（备份不可写）
    ↓
DB/Engine/SharedState applied/settings watch/DTO 全部保持 last-known-good
    ↓
排除名单不变；采集按旧 Settings 恢复 Running
    ↓
留下 Settings 来源的 SETTINGS_SAVED_NOT_APPLIED 诊断
    ↓
故障修复后重试同一 revision 恰好提交一次
```

### 5.3 control accepted 后 failure（4.3.1 语义，4.4 不削弱）

```text
Writer ack 在 8s 内未返回 / ack Closed
    ↓
结果未知（不得声称未提交），锁存 writer_fault
    ↓
本进程内后续 transition 全部 fencing
    ↓
DB 已提交但 watch/最终 publish 失败：保留已提交 revision 并安全停止
    ↓
不伪装 LKG 或回滚已提交事实
```

## 12. 阶段 4.4 复审补修（2026-07-27）

### 12.1 P1-01：根因与修复

**根因**：WriterTask 的 `drain_to_barrier()` 在 `process_data()` 锁存 `protocol_violation`
后仍继续寻找匹配 Barrier。找到后 `verify_engine_revision()` 只校验 Engine revision，
不检查协议健康状态。随后控制分支（Lifecycle/SettingsApplied）仍可能提交边界。

**危险时序**：
```text
① 旧 revision 数据进入 data lane
② Settings/Lifecycle control 进入 control lane
③ Writer 在 drain_to_barrier 中通过 process_data 处理旧数据
④ 旧数据触发 SETTINGS_CONFLICT + protocol_violation + mark_fatal
⑤ drain_to_barrier 继续排空（← 4.4 初版 bug：此处继续）
⑥ 找到匹配 Barrier
⑦ verify_engine_revision：Engine revision 仍 == expected_revision
⑧ 返回 Ok → Settings revision 或 Lifecycle 边界被错误提交
```

**修复位置**（`apps/agent/src/writer_task.rs`）：

| 位置 | 修复 |
|---|---|
| `drain_to_barrier()` 入口、访问 pending/FIFO 前 | 第二次复审补修：已锁存 fault 的任意新 control 立即返回 `SETTINGS_CONFLICT`，不再等待 5s Barrier timeout |
| `drain_to_barrier()` 循环中 `process_data()` 之后 | 新增 `protocol_violation` 检查：一旦锁存立即返回 `SETTINGS_CONFLICT`，停止寻找 Barrier |
| `PendingTake::Matched` 返回成功前 | 新增 `ensure_protocol_healthy()` 检查（belts） |
| FIFO 匹配返回成功前 | 新增 `ensure_protocol_healthy()` 检查（belts） |
| Lifecycle 控制 handler：drain 成功后、`engine.handle()` 前 | 新增 `ensure_protocol_healthy()` 检查（suspenders）；drain 错误分支保留原始错误码不覆盖 |
| SettingsApplied 控制 handler：drain 成功后、`apply_settings_persistent()` 前 | 新增 `ensure_protocol_healthy()` 检查（suspenders） |
| 新增 `protocol_fault_error()` | 返回 `SETTINGS_CONFLICT`（永不覆盖为 `INTERNAL_SAFE_ERROR`） |
| 新增 `ensure_protocol_healthy()` | 统一协议健康守卫 |

### 12.2 protocol fault 状态模型

```text
protocol_violation = false（正常）
    ↓ 首次 revision 错配到达
    ↓ reject_protocol_violation() →
    ↓   protocol_violation = true
    ↓   mark_fatal（Writer/Process Faulted, Capture Stopped）
    ↓   SETTINGS_CONFLICT 诊断
    ↓
protocol_violation = true（不可逆，本进程内永久锁存）
    → 全部后续数据消息拒绝（无论 revision 是否匹配）
    → drain_to_barrier 立即失败
    → 全部 Lifecycle/SettingsApplied/SystemEvent 拒绝
    → 仅 Agent 重启可恢复
```

### 12.3 Settings/Lifecycle 拒绝时序

```text
Control 进入 Writer
    → drain_to_barrier()
        → [control-first] FIFO 排空 → process_data(rev-0) → protocol_violation
            → 立即返回 SETTINGS_CONFLICT
        → [pending-first] pending Matched → ensure_protocol_healthy → Err
        → [FIFO] Barrier 匹配 → ensure_protocol_healthy → Err
    → 返回 Err 给 control handler
    → ack.send(Err(SETTINGS_CONFLICT))
    → DB/Engine/applied/watch 不变
```
