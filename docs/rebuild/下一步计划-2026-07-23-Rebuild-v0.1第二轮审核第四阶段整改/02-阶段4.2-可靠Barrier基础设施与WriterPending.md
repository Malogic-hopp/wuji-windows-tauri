# 阶段 4.2：可靠 Barrier 基础设施与 Writer pending

## 阶段目标

关闭 P1-03 的底层可靠性部分：Barrier 进入 Sample FIFO 必须有明确确认，Writer
不得吞 Barrier，pending 必须有界、可过期、可诊断。

本阶段建立可靠基础设施和低层测试，但不统一所有业务控制入口。

## 必须实现

1. 引入 `BarrierRequest`，包含 `BarrierToken` 与 injected ack。
2. Capture Loop 仅在 Barrier 成功写入 `CapturePipelineItem` FIFO 后确认成功。
3. 请求 channel/FIFO Full、Closed、Capture Loop 或 Processor 退出都有稳定失败。
4. 删除所有忽略结果的 Barrier `try_send`；一次请求只生成一个 BarrierId。
5. Writer 普通 data 分支遇到 Barrier 时登记 pending，不得跳过。
6. pending 按 BarrierId 索引并定义：
   - 容量；
   - TTL；
   - 重复；
   - ID 冲突；
   - overflow；
   - shutdown 清理。
7. Writer 按 ID + kind + expected revision 匹配。
8. 注入失败时不得留下永久等待的 WriterControl。

## 必测场景

- Barrier 在 control 前抵达；
- 同 kind 不同 ID；
- 同 ID 不同 kind/revision；
- request/FIFO closed；
- pending overflow/TTL/重复；
- Processor/Writer 退出；
- Capture/Writer queue 满时 Barrier 仍可达；
- Writer 超时不提交边界。

## 验收标准

- Writer 中不存在普通分支吞 Barrier 的代码；
- Barrier 发送结果均被处理；
- pending 行为有确定性测试；
- 当前生产路径即使尚未统一 Coordinator，也不得比整改前更不可靠；
- fmt/check/clippy 和 Barrier 专项测试通过。

## 明确不做

- 不在本阶段设计 desired/effective capture；
- 不统一 CommandServer/reconciler/Lock-Sleep；
- 不实现 Settings effectivity；
- 不运行全量 soak。
