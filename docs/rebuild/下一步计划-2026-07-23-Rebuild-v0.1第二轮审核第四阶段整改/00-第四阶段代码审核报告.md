## 1. 结论

**本阶段审核结论：不通过。**

当前修改已恢复到可格式化、可编译状态，大部分自动测试通过，`BarrierId` newtype、Capture Loop 单 FIFO 类型、Processor Barrier 透传、Writer 按 ID 排空等局部能力也已出现。但是，S2-04 所要求的统一 Coordinator、可靠 Barrier 注入、Settings effectivity 和失败闭环仍未进入真实生产接线；S2-03 Lock/Sleep 也处于明显未完成状态。

此外，新的 Settings 双槽备份方案没有把 SQLite 中已提交的 revision/digest 纳入启动对账，存在在备份或 settings 文件丢失后静默回退 revision 0、重新使用默认排除名单的风险。该问题触及隐私与 revision 单调性，应作为最高优先级阻断项。

因此当前不得：

1. 将 S2-03 或 S2-04 标记为完成；
2. 将 Rebuild v0.1 标记为整改完成或验收完成；
3. 使用 2026-07-22 的 package/8 小时 soak 证据证明当前工作区；
4. 进入下一功能阶段或生产 cutover；
5. 删除旧 WPF/C#/Bridge 回滚入口。

## 2. 已确认的正向进展

以下改动方向正确，但不足以关闭 S2-04：

1. `BarrierId` 已改为封装 ULID 的受验证 newtype。
2. Capture Loop 到 Processor 已使用 `CapturePipelineItem::{Sample, Barrier}` 单 FIFO。
3. Processor 对 Barrier 使用阻塞发送，避免 Writer data lane 满时直接丢弃 Barrier。
4. WriterControl 已携带 `BarrierId`，`drain_to_barrier` 已按 ID + kind 匹配。
5. ActivityEngine 已拒绝 Observation revision 与当前引擎 revision 不一致。
6. SQLite 不再保存完整 Settings 内容，排除应用名已迁移到独立双槽备份文件。
7. Rust 格式、编译、Clippy、专项测试，以及 React typecheck/lint/test/build 当前可通过。

这些属于局部实现进展，不代表真实运行拓扑和失败语义已经闭环。

## 3. 阻断性问题

### P1-01：Settings last-known-good 丢失时会静默回退 revision 0

涉及文件：

- `rebuild/apps/agent/src/main.rs:101-137`
- `rebuild/apps/agent/src/settings_store.rs:61-102`
- `rebuild/apps/agent/src/settings_store.rs:193-202`
- `rebuild/apps/agent/src/writer_task.rs:149-164`
- `rebuild/crates/wuji-storage/src/writer.rs:221`

Agent 已经打开 SQLite Writer，但启动对账只接收 settings 文件和双槽备份，没有调用已有的 `latest_settings_revision_digest()` 读取数据库最大已应用 revision/digest。

`reconcile_startup_settings()` 又把 `backed_up == None` 转换为 `Settings::default()`。因此存在以下错误路径：

1. SQLite 已提交 revision 5；
2. Settings 双槽备份丢失或损坏；
3. settings 文件缺失、损坏，或只剩较低 revision；
4. Agent 把该状态当成全新 revision 0；
5. `capture_allowed=true`，Capture 可以使用默认排除名单启动；
6. SharedState 的 applied revision 被重置为 0。

这违反：

- revision 不得降级；
- last-known-good 不可恢复时必须阻止采集；
- excludedProcessNames 不得因恢复失败被静默清空；
- Diagnostics/IPC 必须暴露稳定安全错误。

当前名为 `unrecoverable_last_known_good_blocks_capture` 的测试实际断言 `capture_allowed=true`，测试名称与行为相反。

另一个一致性窗口是：Writer 先提交 settings revision，再写双槽备份；备份失败仅输出 stderr，仍然返回 SettingsApplied 成功。这样可以稳定制造“数据库 revision 已前进，但对应完整 Settings 不可恢复”的状态。

整改要求：

1. 启动对账必须同时输入 SQLite 最大 revision/digest、settings 文件和双槽备份。
2. 数据库最大 revision > 0 时不得退回默认 revision 0。
3. 文件或备份只有在 revision/digest 与数据库 metadata 一致，或是合法的严格前滚 revision 时才可使用。
4. 如果既无法恢复数据库当前 revision，也没有合法前滚文件，必须：
   - `capture_allowed=false`；
   - effective capture 保持冻结；
   - 上报来源明确的 `SETTINGS_INVALID` 或 `SETTINGS_CONFLICT`；
   - IPC 保持在线以便修复。
5. Settings commit 与备份需要 crash-consistent 协议。可采用“先持久化候选备份，再提交 SQLite，启动时仅信任与 SQLite metadata 匹配的槽位”等方案，但不得在备份失败后返回完整成功。
6. 增加数据库 revision 高于文件/备份、双槽全损坏、备份写失败、commit 前后崩溃点的确定性测试。

### P1-02：CaptureCoordinator 未进入生产接线，且自身没有执行冻结/恢复

涉及文件：

- `rebuild/apps/agent/src/main.rs:149-213`
- `rebuild/apps/agent/src/command_server.rs:162-176`
- `rebuild/apps/agent/src/settings_reconciler.rs:22-101`
- `rebuild/apps/agent/src/capture_coordinator.rs:68-179`

`main.rs` 没有创建 `CaptureCoordinator`。CommandServer、settings reconciler、Windows session/power pump 仍分别持有并直接操作：

- `control_tx`
- `capture_state_tx`
- `barrier_request_tx`
- 独立 `capture_lock`

因此 Lifecycle、settings_reload、reconciler、Lock/Sleep 之间没有共享 transition lock，无法证明控制操作的顺序与失败原子性。

即使接入当前 Coordinator，它的两个 apply 方法也没有执行注释所称的“冻结/恢复”。`capture_state_tx` 只被保存和暴露，没有在 apply 流程中使用；`_desired` 读取后立即丢弃；desired/user state、系统抑制状态与 effective capture gate 没有独立建模。

整改要求：

1. `main.rs` 创建唯一 `Arc<CaptureCoordinator>`。
2. CommandServer、reconciler、Lock/Sleep 全部只通过 Coordinator 执行状态变更，不再直接发送 WriterControl 或 Barrier。
3. 删除分散的 `capture_lock` 和重复控制路径。
4. Coordinator 必须保存或访问以下独立状态：
   - 用户 desired capture state；
   - session locked 抑制；
   - system sleeping 抑制；
   - effective capture gate；
   - 当前 applied settings revision。
5. Settings/Lifecycle 失败后 shared/watch/DTO 必须一致；不得出现 watch 已 Paused、SharedState 仍 Running，或 DB 已前进、Processor watch 仍旧值。

### P1-03：Barrier 可被吞掉、静默丢失或形成幽灵 pending

涉及文件：

- `rebuild/apps/agent/src/command_server.rs:231-265`
- `rebuild/apps/agent/src/command_server.rs:331-347`
- `rebuild/apps/agent/src/settings_reconciler.rs:65-84`
- `rebuild/apps/agent/src/capture_loop.rs:169-181`
- `rebuild/apps/agent/src/writer_task.rs:238-288`
- `rebuild/apps/agent/src/writer_task.rs:291-327`

当前存在多条不可靠路径：

1. Capture Pause/Stop 和 reconciler 对 `barrier_request_tx.try_send()` 的结果继续忽略。
2. `settings_reload` 连续创建并注入两个不同 ID 的 Settings Barrier：
   - 第一个 Barrier 没有任何对应 WriterControl；
   - 第二个 Barrier 才与 control 使用同一 ID。
3. Coordinator/CommandServer 的 Barrier 请求 send 只证明请求进入控制 channel，不证明 Capture Loop 已把 Barrier 成功写入 Sample FIFO。
4. Writer 普通 data 分支遇到 `ProcessorOutput::Barrier` 时直接返回，Barrier 比 control 先到达时会被永久吞掉。
5. `pending_barriers` 是容量 64 的 Vec：
   - 超过容量静默丢弃；
   - 没有 TTL；
   - 没有重复 ID/不同 kind/不同 revision 冲突检测；
   - 没有退出时失败回收。
6. `drain_to_barrier` 只匹配 ID + kind，没有验证 `expected_revision`。

真实后果包括：

- Barrier 已进入 FIFO，但 control 尚未来得及发送时被 Writer 普通分支吞掉；
- control 随后等待 5 秒并超时；
- IPC 3 秒先返回 timeout，但后台副作用继续悬挂；
- Capture watch、SharedState、Writer Engine 出现不同状态；
- 幽灵 Barrier 长期占用 pending 容量。

整改要求：

1. 引入 `BarrierRequest { token, injected_ack }`。
2. Capture Loop 仅在 Barrier 成功写入与 Sample 相同的 FIFO 后发送 injected ack。
3. Barrier 请求必须使用可靠 await send；Full/Closed/任务退出均返回稳定错误。
4. Coordinator 只有在收到 injected ack 后才登记/发送对应 WriterControl，或采用等价的无悬挂协议。
5. Writer 普通 data 分支遇到 Barrier 必须登记 pending，不得跳过。
6. pending 使用按 BarrierId 索引的有界结构，具备 TTL、重复/冲突检测和显式错误。
7. Writer 按 ID + kind + expected revision 三者匹配。
8. Processor、Capture Loop、Writer 或 control lane 退出时，所有等待方必须得到确定失败。

### P1-04：Settings effectivity 仍不成立

涉及文件：

- `rebuild/apps/agent/src/processor_task.rs:25-49`
- `rebuild/apps/agent/src/command_server.rs:331-365`
- `rebuild/apps/agent/src/settings_reconciler.rs:65-95`
- `rebuild/apps/agent/src/writer_task.rs:307-327`

Processor 检测到 `RawCapture.settings_revision` 与当前 Settings revision 不一致后，仍继续使用当前 Settings 处理样本。注释明确写着“错配时仍按当前 settings 处理”。

同时 Settings 切换没有冻结 Capture。Barrier 进入 FIFO后，Capture Loop 仍可能在 Settings watch 更新前产生旧 revision 样本。Writer 在 Barrier 处先应用新 Settings，随后：

- Observation 因 revision 不匹配被拒绝，造成静默数据损失；
- PrivacyExcluded/CaptureError 虽携带 revision，却在 Writer 转换 EngineEvent 时被忽略 revision，仍按新引擎状态写 gap；
- excludedProcessNames、idle threshold、work threshold 可能在错误边界生效。

整改要求：

1. Settings 切换必须冻结 effective capture。
2. Barrier 前的全部 Sample 必须按旧 Settings 处理并写旧 revision。
3. Writer 成功提交 Settings 后，先更新 Settings watch，再恢复 effective capture。
4. Processor 遇到 revision 错配必须显式失败并上报诊断，不得使用不匹配的当前 Settings 继续处理。
5. 所有 ProcessorOutput 数据变体都必须接受 revision 校验：
   - Observation；
   - PrivacyExcluded；
   - CaptureError。
6. ActivityEngine/SQLite 不得把旧样本静默重标为新 revision。
7. 增加 excludedProcessNames、idle threshold、work threshold 的边界前后测试。

### P1-05：S2-03 Lock/Sleep 尚未完成

涉及文件：

- `rebuild/apps/agent/src/main.rs:215-278`
- `rebuild/crates/wuji-windows/src/session_power.rs`

`main.rs` 注释已经明确说明“S2-03 将添加 Capture 冻结和恢复逻辑”。当前 Lock/Sleep 路径：

1. 不冻结 effective capture；
2. `expected_revision` 硬编码为 0；
3. 丢弃 Writer ack；
4. Lock/Sleep Barrier 或 control 失败时不更新 SharedState 错误；
5. Unlock/Resume 不改变抑制状态或恢复 effective capture；
6. 没有处理与用户 Pause/Stop 的叠加关系。

这会导致锁屏期间继续采样，并可能在生命周期 gap 已打开后继续写 Observation。

此外，当前电源事件使用 message-only window 接收广播式 `WM_POWERBROADCAST`，需要通过真实手工测试确认该窗口形态能收到 Suspend/Resume；若不能，应改用可接收广播的隐藏顶层窗口或 Windows suspend/resume 注册 API。现有自动测试只验证事件泵可以启动，没有证明真实 Sleep/Resume 事件会到达。

整改要求：

1. Lock/Sleep 必须通过统一 Coordinator。
2. Lock/Sleep 设置系统抑制并冻结 effective capture。
3. Unlock/Resume 只移除对应抑制；仅当 desired state 为 Running 且其他抑制均解除时恢复。
4. Pause/Stop 期间发生 Lock/Sleep 不得覆盖用户 desired state。
5. expected revision 来自 Coordinator 当前 applied revision，不得硬编码。
6. 必须等待 Writer ack，并把失败写入来源明确的安全错误。
7. 自动测试覆盖状态叠加；真实 Lock/Sleep 仍保留为手工门禁，不得伪造完成。

## 4. 其他重要问题

### P2-01：真实拓扑测试仍不足

涉及文件：

- `rebuild/apps/agent/tests/settings_lifecycle.rs`
- `rebuild/apps/agent/tests/writer_watermark.rs`
- `rebuild/apps/agent/tests/ipc_protocol.rs`

当前多数 Barrier 测试直接向 Writer data lane 注入 `ProcessorOutput::Barrier`。reconciler 测试使用人工转发任务把 BarrierToken 直接包装为 ProcessorOutput，也没有覆盖真实 Capture Loop 和 Processor。

因此现有测试无法捕获：

- Barrier 在 control 前到达后被普通 Writer 分支吞掉；
- `try_send` Full/Closed 静默失败；
- Settings watch 更新前的 Barrier 后旧 revision 样本；
- CommandServer、reconciler、Lock/Sleep 并发；
- Coordinator 未接入 main；
- in-flight Win32 capture 与冻结竞争。

至少需要覆盖第三阶段回应中列出的 17 类场景，并确保核心用例走真实：

`CaptureCoordinator → BarrierRequest → Capture Loop → CapturePipelineItem FIFO → Processor → Writer data lane + Writer control lane`

Writer 单元测试可以保留，但不能替代真实接线测试。

### P2-02：完整 Rust 全量测试仍有 flaky

`agent_survives_parent_exit_and_offline_read_works_after_kill`：

- 单独串行执行时通过；
- 完整 `cargo test --workspace` 再次在“必须定位到 Agent 进程”处失败；
- 跳过该项后 workspace 其余测试全部通过。

因此不能写成“一次完整 workspace 全绿”。应使用确定性进程身份或句柄同步替代全局进程扫描和时序猜测，并保留首次失败记录。

### P2-03：soak 脚本仍可能产生优雅退出假阳性

涉及文件：

- `rebuild/scripts/soak.py:318-328`
- `rebuild/scripts/soak.py:363-386`

`ipc_graceful_shutdown()` 返回失败时，脚本只打印错误，没有把 `ok == false` 加入 `failures`。如果 Agent 随后以 exit code 0 退出，报告仍可能给出 `verdict=pass`，与脚本声明的“hello 和 shutdown 两次响应都必须成功”不一致。

需要持久记录：

- shutdown 是否实际执行；
- hello 是否 ok；
- shutdown 是否 ok 且 `willExit=true`；
- 是否在 grace time 内 exit code 0；
- 是否发生强杀。

上述任一项失败都必须进入 `failures`。

## 7. 通过条件

下一轮只有同时满足以下条件才能关闭 S2-03/S2-04：

1. main 生产路径中只有一个 Coordinator 控制 Lifecycle、Settings、reconciler、Lock/Sleep。

3. Barrier 注入有 injected ack，Full/Closed/任务退出均有稳定失败。
