## 二、P1-01：彻底消除 SessionPowerBridge shutdown 的无界等待

### 2.1 当前根因

当前 `SessionPowerBridge::shutdown()` 仍有以下阻断链：

```text
request_stop() 结果被忽略
→ 等待 pump exited 超时
→ join_finished() 在未 finished 时消费并丢弃 pump JoinHandle
→ 无条件 bridge_thread.join()
→ pump 若仍持有 events sender，bridge 仍阻塞在 recv()，join 永久等待
```

此外，consumer supervisor timeout 后只调用 abort，没有再次有界等待其退出；
`shutdown()` 返回 `()`，调用方无法判断 stop 投递失败、pump timeout、bridge timeout
或残留清理责任。

### 2.2 必须采用的有界所有权模型

允许调整具体类型名，但必须满足以下不变量：

1. `SessionPowerPumpHandle::request_stop()` 改为返回 `io::Result<()>` 或等价结构化错误，
   不再以被调用方忽略的 bool/eprintln 作为唯一结果；
2. pump、bridge、consumer/supervisor 各自有异步 `exited` 信号；正常返回、错误和
   panic 路径由 RAII exit guard 尽力发送；
3. 对 Tokio `JoinHandle` 使用 `timeout(..., &mut handle)` 或等价方式，timeout 后仍
   持有 handle；不得因为 timeout 消费并 detach；
4. 对 std thread 只能在收到 exited 或 `is_finished()==true` 后同步 join；join 只做
   回收，不承担等待；
5. pump timeout 后不得继续无条件 join bridge；bridge timeout 后也不得无界 join；
6. 若正常 `PostMessageW(hwnd, WM_APP_SHUTDOWN)` 失败，提供明确的有界兜底，例如保存
   pump thread id 并投递 `WM_QUIT`；兜底失败也必须形成结构化诊断；
7. `shutdown()` 返回 `Result<ShutdownReport, ShutdownError>` 或等价结果，报告
   consumer/pump/bridge 是否退出、是否使用兜底、是否仍持有未回收句柄；
8. timeout 后必须保留清理责任。可使用 `shutdown(&mut self)` 使对象仍持有句柄，或
   在错误结果中返回 residual handles；不得静默 detach 后宣称 shutdown 完成；
9. 正常 shutdown 不锁存 monitor fault；stop 投递失败、任务异常退出或无法有界回收
   必须锁存 `lifecycle_monitor_fault` 并设置 `ErrorSource::LifecyclePump`；
10. 更新 `main.rs`：检查 shutdown 结果并记录准确诊断，同时保证 Agent 总关闭流程
    不会因 lifecycle bridge 永久阻塞。

不得把 3s/5s 改大作为修复。问题是 timeout 后的所有权和无界 join，不是等待时间
不够。

### 2.3 必须新增的确定性测试

将 shutdown 编排抽成生产与测试共用的小组件或可注入窄接口，至少覆盖：

1. 正常 stop：consumer、pump、bridge 三层均退出并被回收，报告 Complete；
2. `PostMessageW`/request_stop 明确失败：启用有界兜底，结果和诊断准确；
3. pump 永不发送 exited：外层 deadline 内返回 Incomplete/Error，不执行 bridge
   无界 join；
4. bridge 被钉在 recv 或 blocking_send：shutdown 有界返回，不创建永久
   `spawn_blocking`；
5. consumer timeout：abort 后再次有界等待确认，不能只发 abort 就丢 handle；
6. pump/bridge/consumer panic：supervisor 锁存 monitor fault；
7. 正常生产 `start_session_power_bridge()` → `shutdown()` 必须包在测试外层
   `tokio::time::timeout` 中，超时即确定性失败；
8. 测试 runtime drop 后无线程和 Agent 残留。

`wuji-windows` 中现有 `thread::sleep(200ms)` 的 pump 测试也必须改成 exited
rendezvous，不允许依赖固定睡眠。

## 四、P1-03：重写 L16，制造真正正在执行的 capture

当前 `GatedSource` 在 gate 打开时立即返回 CaptureError，并未阻塞一次已经开始的
`capture()`；测试又在调用 Lock 前先设置 gate，因此没有形成 in-flight 竞争。

推荐实现：

1. 新建 `BlockingCaptureSource`：
   - `capture()` 开始时通过 rendezvous 通知测试“已进入”；
   - 随后阻塞等待 release 信号；
   - release 后返回带唯一 canary/sequence 的有效 RawSample；
2. 本测试必须启用生产相同的 `offload_capture=true`，避免同步 capture 阻塞 Tokio
   runtime；
3. Start 后推进到采样点，等待 `capture_entered`；此时 capture 已开始但尚未返回；
4. 并发发起 Lock，证明 Coordinator 已 freeze 且 Lock future 尚未完成；
5. 在明确 rendezvous 后释放 capture；
6. 证明 FIFO 顺序为迟到 capture item → Barrier，Writer 边界不会被该样本越过；
7. SQLite 证据必须区分：
   - canary Observation 若被接纳，只能属于边界前 revision/sequence；
   - Lifecycle gap 只提交一次；
