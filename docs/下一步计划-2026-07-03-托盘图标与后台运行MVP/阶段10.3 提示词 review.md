# 建议补强 1：关闭拦截后不要触发 Closed 事件里的清理

10.2 可能已经有 `window.Closed` 里做 `StopStatusPolling + Dispose TrayService`。10.3 中如果 `Closing` 被取消并 `Hide`，理论上不会触发 `Closed`，但建议明确：

```text id="unnsbl"
CloseToTray 拦截时必须设置 e.Cancel=true 并 Hide，不得调用 Close()，不得触发 Window.Closed 清理路径。
```

这样能防止 agent 用“Close 后再 Show”的错误方式实现隐藏。

---

# 建议补强 2：最小化隐藏时避免重复 Hide / 状态抖动

`StateChanged` 里处理 MinimizeToTray 时，容易发生重复触发。建议补一句：

```text id="m1gdb4"
MinimizeToTray 处理时，如果窗口已经不可见或正在显式退出，应直接返回；避免重复 Hide 或退出过程中误拦截。
```

这能减少边界 bug。

---

# 建议补强 3：Show 时要恢复 `ShowInTaskbar`

如果 Hide 到托盘时改过 `ShowInTaskbar`，Show 时要恢复。即使当前不改，也建议明确：

```text id="96mh3n"
如果 Hide 到托盘时设置了 ShowInTaskbar=false，Show Main Window 时必须恢复 ShowInTaskbar=true。
如果本阶段不修改 ShowInTaskbar，也需在完成说明中说明。
```

否则窗口可能恢复了但任务栏不可见。

# 建议补强 5：AppSettings 运行时变更的读取来源要明确

你写了“运行时如修改设置，下一次关闭/最小化行为按新设置生效”。这很好，但实现上要避免读旧缓存。建议补一句：

```text id="y51vfj"
Close/Minimize 判断应读取当前已加载的 AppSettings / SettingsService 最新值，或在 Settings 保存后同步更新 MainWindow/App 层缓存；不得只读取启动时旧值导致设置保存后不生效。
```

如果现有 Settings 保存流程已经更新了缓存，就复用即可；不要新加 schema。

# 建议补强 6：测试不要过度追求真实 Window

你要求不要启动真实 WPF App，但 Close/Minimize 本质是窗口事件，自动化可能不容易。建议给 agent 一个可测试抽象：

```text id="btxttg"

```

这能减少为了测试真实 WPF 窗口而写脆弱测试。
