## 2. 当前生产时序与可复用基础

当前 `CaptureCoordinator::apply_settings` 已具备以下骨架：

```text
唯一 transition lock
→ transition suppression 冻结 effective capture
→ Capture Loop 将 Barrier 写入唯一 CapturePipelineItem FIFO 并 ack
→ Processor 原样转发 Barrier
→ Writer 排空到 Barrier
→ crash-consistent 提交 Settings
→ SharedState.applied revision 前进
→ Writer ack
→ settings watch send_replace
→ PipelineHealth/通道检查
→ 按 desired/suppression 恢复 effective capture
```

这条骨架应继续作为 4.4 的唯一边界，不得另建 settings lock、第二条 Barrier、
直接 WriterControl 或绕过 Coordinator 的 watch 更新路径。

## 3. 代码实审确认的 4.4 缺口

### G4-01：Processor revision 错配仍继续处理

`apps/agent/src/processor_task.rs` 当前先借用“此刻的 settings watch”处理
`RawCapture`，发现 `raw.settings_revision != current_revision` 后只有空分支注释，
仍按当前 Settings 产生输出。这会使旧样本被新隐私/idle 规则解释，违反 P1-04。

最低修复：在调用 `ObservationProcessor::process` 前比较 revision；错配必须产生
明确、可诊断、fail-closed 的协议失败，绝不能继续处理、静默丢弃或把 revision
重标为当前值。

### G4-02：Writer 只校验 Observation

`apps/agent/src/writer_task.rs::process_data` 目前只检查
`FilteredObservation.settings_revision`；`PrivacyExcluded` 与 `CaptureError` 虽携带
revision，却在转换成 EngineEvent 时被直接丢弃。三类数据必须共用同一 revision
防线，错配不得改变 ActivityEngine 或 SQLite。

### G4-03：现有 watermark 测试多为手工 lane 注入

`settings_lifecycle.rs` 已证明部分 Writer watermark、降级、备份失败和 reconciler
行为，但多数测试直接构造 `ProcessorOutput`/`WriterControl`，没有证明真实
Coordinator + Capture FIFO + Processor + Writer 的端到端 effectivity。

### G4-04：规则语义缺少边界前后证据

当前没有一组真实拓扑测试同时证明：

- excludedProcessNames 添加/移除；
- idle threshold 改变；
- work-break threshold 改变；
- Observation / PrivacyExcluded / CaptureError；
- DB、Engine、SharedState、settings watch、DTO；

都在同一个 Settings Barrier 上从旧 revision 原子切换到新 revision。

### G4-05：commit/watch/消费者退出后的 LKG 证据仍需扩展

4.3.1 已定义 unknown/fail-closed，但 4.4 还要证明 Settings 提交明确失败时，旧
DB revision、ActivityEngine settings、SharedState applied、settings watch 与 DTO
保持一致；修复故障后重试只提交一次且边界前数据不被重新解释。

## 4. 推荐实现方案

### 4.1 保留 Barrier 边界，不给旧样本套用新 Settings

优先保留现有“冻结 + 单 FIFO Barrier + Writer drain + 提交后发布 watch”模型。
正确时序保证 Writer ack 前：Capture 不生产新样本，Processor 已处理完 Barrier
前的旧样本，Writer 已提交完旧 backlog；watch 更新后才恢复 Capture。

不要用以下方式掩盖问题：

- 在 Processor 中把旧 revision 改成当前 revision；
- mismatch 时继续调用当前 Settings；
- 清空整个队列或静默 drop；
- 给 Barrier 后数据延迟套用旧 Settings；
- 再建一个 settings lane/lock 绕过单 FIFO。

### 4.2 建立统一 revision 访问与 Writer 防线

建议为 `ProcessorOutput` 增加统一的 `settings_revision() -> Option<i64>`（Barrier
返回 None），Writer 在转换任何 EngineEvent 前统一校验 Observation、
PrivacyExcluded、CaptureError。

错配属于内部协议不变量破坏，推荐行为：

1. 不调用 ActivityEngine，不写 SQLite；
2. 设置来源明确的 `SETTINGS_CONFLICT` 诊断；
3. fail-closed 停止采集并锁存不可在本进程内自动解除的流水线 fault；
4. IPC/Diagnostics 保持在线；
5. 记录 sequence、expected/actual revision 的安全诊断，但不得记录原始窗口标题等
   隐私内容。

Processor 自身也必须在业务处理前拒绝 mismatch。可采用显式内部 mismatch 消息交给
Writer 统一 fatal，或由 Processor 设置诊断并退出、再由 pipeline supervisor
fail-closed；无论选择哪种，必须用测试证明没有静默 drop、没有当前 Settings 误处理、
没有后续旧 revision 输出。

### 4.3 Settings 发布与恢复

- Writer 成功 ack 前不得更新 settings watch。
- watch 更新后、恢复 Running 前必须再次通过 PipelineHealth、capture/control/
  settings consumer 检查；现有 `publish()` 与 supervisor 不得削弱。
- commit 明确失败：走 last-known-good，可重试；不得前进 applied/watch/DTO，不得
  修改 Engine revision。
- control accepted 后 ack Closed/timeout/cancel：沿用 4.3.1 unknown fencing，不能
  在 4.4 中改回“未提交”。
- DB 已提交但 watch/最终 publish 失败：保留已提交 revision并安全停止，不伪装
  LKG 或回滚已提交事实。

## 5. 确定性测试矩阵

至少新增一个真实拓扑 fixture：使用唯一 `CaptureCoordinator`、真实 Capture Loop、
真实 Processor、真实 Writer、临时 v0.1 SQLite 和 paused Tokio 时钟；采集源可脚本化，
但不得绕过 Capture FIFO。所有等待使用 channel/watch/queue-depth/SQLite 条件作为
rendezvous，不使用随机 sleep。

| 编号 | 场景 | 必须证明 |
|---|---|---|
| E01 | revision 0→1 | Barrier 前输出/DB 为 0；Barrier 后首条及以后为 1；无旧 revision 穿越 |
| E02 | excluded 添加 | 同进程名在边界前是 Observation，边界后是 PrivacyExcluded(rev1) |
| E03 | excluded 移除 | 边界前 PrivacyExcluded，边界后恢复 Observation；不泄露隐私字段 |
| E04 | idle threshold 改变 | 同一 idle reading 在边界两侧按各自 Settings 分类，revision 对应正确 |
| E05 | work-break threshold 改变 | ActivityEngine/SQLite work block 只从新边界后的事件采用新阈值 |
| E06 | CaptureError 边界 | 边界前后 CaptureError 携带并校验各自 revision |
| E07 | Processor 三类 mismatch | Observation/PrivacyExcluded/CaptureError 均显式失败；零 DB 副作用；流水线 fail-closed |
| E08 | Writer 三类 mismatch | 防御性校验覆盖三类输出；ActivityEngine 状态与 DB 不变 |
| E09 | commit 失败 | DB/Engine/applied/watch/DTO 保持旧 revision；排除名单不被清空 |
| E10 | 故障修复后重试 | 同一目标 revision 最终恰好提交一次；没有重复边界或旧消息重标 |
| E11 | watch/Capture/Processor 消费者退出 | 已提交与未提交两类语义严格区分；不得虚假 Running |
| E12 | IPC reload × reconciler | 继续共用唯一 Coordinator；并发目标 revision 只产生一个有效提交 |

完成说明必须用表格列出三类 `ProcessorOutput` 在 Barrier 前后的：sequence、
settings revision、实际 Settings 规则、Engine revision、SQLite 结果和失败诊断。
