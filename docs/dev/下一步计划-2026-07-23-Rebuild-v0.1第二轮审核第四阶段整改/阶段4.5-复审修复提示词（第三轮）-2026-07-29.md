## 二、P1-01：修复专项测试 harness 与四项真实失败

### 2.1 L09：Barrier 注入明确失败后，在同一个 Coordinator 上重试

当前测试第一次失败与第二次所谓“重试”使用两个不同的 Coordinator，因此第二次
实例不可能复用第一次保存在 `LockSleepState.first_at_utc_ms` 中的首次时间；测试
还存在先 await Coordinator、之后才读取 control/发送 ack 的错误时序，必然走
Writer ack unknown timeout。

重写要求：

1. 整个测试只创建一个 Coordinator，并保持同一份 suppression 状态；
2. 使用可控的 Barrier consumer：第一次请求返回明确注入失败，证明 control lane
   没有收到 `WriterControl`、DB 没有边界、active 与首次时间 T0 保留；
3. 修复注入端后，用更晚的事件时间 T1 在**同一个 Coordinator**上重复 Lock；
4. 并发启动第二次 apply，再从 control receiver 读取
   `WriterControl::Lifecycle`，断言其中 EngineEvent 时间仍等于 T0，然后发送 Writer
   ack；不得先 await apply 再消费 control；
5. 最终断言边界恰好提交一次，gap start 等于 T0；active+committed 后再次重复 Lock
   幂等，不得产生第二条边界。

### 2.2 L10：control send timeout 后，在同一个 Coordinator 上确定性恢复

当前测试同样使用两个 Coordinator，且消费 control/ack 的时序错误，未证明首次时间
可以跨失败保留。

重写要求：

1. 使用容量 1 的 control lane并预填一条 maintenance/control 占位消息；Barrier
   consumer 必须正常消费请求并返回 injected ack，确保失败点确实是 control send
   timeout；
2. 第一次 Lock 使用 T0，确定性等待 send deadline 到期；断言 Lifecycle control
   未入队、DB 未提交、suppression 与 T0 保留、错误来源准确；
3. 从**同一个 receiver**排空占位消息，不得替换 Coordinator 或 control channel；
4. 用更晚时间 T1 在同一个 Coordinator 上重试，同时消费 Lifecycle control，断言
   EngineEvent 时间为 T0，再发送 Writer ack；
5. 断言成功后只提交一次，并验证重复 Lock 幂等。

paused Tokio 时钟可以用于推进已建立的 deadline，但必须先通过 rendezvous 证明相关
future 已经 poll 到目标等待点；不得依赖固定 `yield_now()` 次数猜测状态。

### 2.3 L11：用确定性 Writer 明确失败证明 Coordinator 语义

当前 SQLite busy + 固定 yield/advance 的注入没有稳定地把 Writer 钉在预期故障点，
因此测试有时并未进入 Writer 明确失败路径。

优先采用以下确定性方案：

- 使用真实 Coordinator 与可控的 mock control responder；
- Barrier 注入成功后，responder 接收真实 `WriterControl::Lifecycle`，明确返回
  `Err(SafeError)`；

  `ErrorSource` 与安全错误码精确；

## 三、P1-02：消除 SessionPowerBridge shutdown 的无界等待

当前 shutdown 时序仍存在阻断风险：

1. `SessionPowerBridge::shutdown()` 在 pump 的 5 秒 timeout 之前执行
   `bridge_thread.join()`；若 pump 未退出，bridge 可能永久阻塞在
   `events_rx.recv()`，后续 timeout 永远无法执行；
2. `spawn_blocking(move || exited.recv())` 在外层 timeout 后不能被取消；Tokio runtime
   关闭时仍可能等待这个永久 blocking task，重新造成 `cargo test --workspace` 卡在
   `agent_e2e.rs` 或测试进程退出阶段；
3. `PostMessageW` 失败目前不能形成足够明确的停止诊断。

要求按以下模型重构：

### 3.1 退出信号与所有权

- pump、bridge、consumer 分别提供异步可等待的退出信号，优先使用
  `tokio::sync::oneshot`（或等价不会永久占用 blocking pool 的异步原语）；
- 退出信号必须由各任务/线程的 RAII guard 在正常返回、错误和 panic unwind 可覆盖的
  路径上发送；
- 保留各自 `JoinHandle` 的清理责任，不能在 timeout 后静默丢弃；
- 不得通过 `spawn_blocking` 包装无限期的 `std::sync::mpsc::Receiver::recv()`。

### 3.2 有界 shutdown 顺序

生产 shutdown 必须清晰实现并记录以下顺序：

1. 发送正常 shutdown signal，避免把正常关闭误报为 monitor fault；
2. 调用 `pump.request_stop()`，并检查 `PostMessageW` 的返回值；失败时返回或记录明确
   Win32 错误，同时继续有界兜底；
3. 在总预算内异步等待 consumer、pump、bridge 的 exited 信号；每一层都必须有
   明确 timeout 与诊断；
4. 只有已收到 exited，或相应 `JoinHandle::is_finished()` 已确认完成时，才允许执行
   同步 `join()`；此时 join 只负责回收，不再承担等待；
5. timeout 后不得执行无界 join。需要保留句柄并报告未回收层，或实施可证明有界的
   兜底退出协议；
6. 正常 shutdown 不锁存 `lifecycle_monitor_fault`；异常退出或无法有界回收必须锁存
   monitor fault，并提供 `ErrorSource::LifecyclePump` 诊断。

不要仅靠增大 5 秒 timeout 修复；问题是等待顺序和不可取消 blocking recv，而不是
时间预算大小。

### 3.3 shutdown 确定性测试

至少补齐：

- pump 正常响应 stop：三层 exited 均到达，shutdown 有界返回，无 monitor fault；
- pump 不响应或 stop 投递失败：shutdown 在预算内返回错误/诊断，不在 bridge join
  处挂起；
- bridge input 未关闭或 bridge 被钉在 send/recv：timeout 路径仍有界，不创建永久
  blocking task；
- consumer 正常/异常退出区分准确；
- 测试 runtime drop 后进程可退出，无残留线程或 Agent 进程。

## 四、P1-03：修正 L16/L18/L19/L20 的测试语义

### 4.1 L16 必须覆盖真正 transition-in-flight 的迟到样本

### 4.2 L18 去掉随机 sleep，使用生产 helper 的确定性背压证据

- 禁止随机 sleep、固定轮询次数或只断言“最终结束”。

### 4.3 L19 查询并关闭正确的 open gap

Lock→Sleep 后，按当前 Engine 语义 `session_locked` 已关闭，最后仍 open 的 gap 是

- 首条 Observation 落库后断言同一条 `system_sleep` gap 被关闭，时间边界正确；
- 不得继续查询已关闭的 `session_locked` 来制造假绿或假失败。

- 另用可注入故障或生产/测试共用 supervisor helper，分别证明 pump、bridge、consumer
  异常退出会锁存 monitor fault，正常 shutdown 不误报。

若 Windows 消息泵的某一失败无法在测试环境确定性构造，必须把失败源抽成窄接口或
