## 2. 修正后的 Capture FIFO 满载时序（§二A）

原测试结论更正：旧版用默认 3 秒采样间隔 + 容量 2 + 推进 2.5 秒，实际最多
1 条 Sample，**从未满载**；且未证明 injected ack 在腾槽前未返回。
修正后时序（全部 paused 时钟 + 确定性事实断言，无随机 sleep）：

```text
① settings 显式 sampling_interval_seconds=1，FIFO 容量 2；
② yield 启动 Capture Loop（paused 下新 spawn 任务的计时器首次 poll 前对
   advance 不可见——本阶段实测确认），advance(1.1s) + yield 后
   continuity.capture_queue_depth()==2（确定性满载证据）；
③ spawn inject_barrier；yield×2 让 Capture Loop 取得请求并阻塞在 FIFO 写入；
④ timeout(100ms, inject) 失败 → 证明腾槽前 injected ack 未返回、FIFO 内容不变；
⑤ 取走一条旧 Sample → inject 返回 Ok；
⑥ FIFO 顺序：剩余旧 Sample 在前、Barrier 在后（逐条断言，不再"扫一轮找 Barrier"）。
```

## 3. Capture/Writer 真实任务退出时序（§二B/§二C）

§二B（Capture Loop 退出）：真实 Capture Loop（FIFO 容量 2 真实满载）→
Coordinator pause → 冻结发布（watch rendezvous）→ loop 取得请求并阻塞 FIFO 写入
→ 确认 transition 未完成 → abort loop → 被持有的 BarrierRequest 随任务销毁
（ack sender 断开）→ inject 返回 `Closed` → **不发送 WriterControl** →
fail-closed（watch/shared/desired 一致 Paused）→ `PipelineHealth.capture=Dead`。

§二C（Writer 真实退出，非 mock ack drop）：

```text
① 第二连接 BEGIN IMMEDIATE 持写锁（真实 SQLite busy 注入）；
② Coordinator capture_start 发布 Running（健康/channel/watch 全通过）；
③ 样本经真实 FIFO/Processor 流入真实 WriterTask（into_run_future 已登记健康）；
④ 写锁使首个 Observation busy（busy_timeout 750ms 一次真实阻塞）→
   Writer Degraded + backoff（paused 停住，rendezvous 点）；
⑤ Coordinator pause：冻结 → Barrier 流经 FIFO/Processor → control 进入
   Writer control lane 缓冲（Writer 仍停 backoff）；
⑥ abort WriterTask → 缓冲中的 control（连同 ack sender）销毁 →
   Coordinator 立即得到稳定失败（控制确认失败），无永久等待；
⑦ 断言：shared/watch/DTO/desired 一致 Paused；writer=Dead；
   capture/processor 仍 Alive；SQLite 无 capture_paused 边界、无已提交
   Observation；ROLLBACK 解锁。
```

## 6. Settings/SystemEvent 最终 publish 失败语义（§三B）

- SystemSleep：`system_event_final_publish_failure_returns_error_and_safe_stops`
  ——Barrier 与 Writer ack 成功（边界已提交，不回滚），最终 publish 前 Capture
  consumer 退出 → `INTERNAL_SAFE_ERROR`（"系统事件已提交但采集流水线不可用"），
  LifecyclePump 诊断，shared/DTO/desired/effective 全部 Stopped。
- Settings：`settings_final_publish_failure_keeps_committed_revision_and_safe_stops`
  ——applied revision 已前进（ack 前按真实 Writer 顺序设 1）、settings watch
  交付成功（保持新 revision 1），Running 解冻发布失败 →
  `INTERNAL_SAFE_ERROR`，applied 保留为 1 不回退，Settings 诊断，安全停止。

## 7. S2-06 状态机、deadline、fencing 与 request cache 规则

### 7.1 有界化总览（不再有永久等待）

| 环节 | 期限（服务端命名，与 IPC 客户端 3s 分离） | 超时语义 |
|---|---|---|
| barrier request send（reserve） | `BARRIER_REQUEST_SEND_TIMEOUT` = 2s | `SendTimeout`；permit 未获得 → 请求保证未进入 channel；不发 control |
| injected ack | `BARRIER_INJECT_ACK_TIMEOUT` = 3s | `AckTimeout`；**不能断言未注入**（可能已入 FIFO 而 ack 丢失）；不发 control；遗留 Barrier 由 pending TTL/冲突规则清理 |
| Writer ack（Coordinator operation deadline） | `WRITER_ACK_TIMEOUT` = 8s（> Writer drain 上限 5s） | **提交结果未知**：锁存 writer_fault、强制 Stopped、 fencing（见 7.2）；不发第二次副作用 |
| IPC 客户端等待 | `REQUEST_TIMEOUT` = 3s（既有，未改） | 只结束本次等待，不取消已接受副作用（R05 合同不变） |
| request cache Wait 分支 | `REQUEST_TIMEOUT` = 3s | 有界等待；条目不删除，重试继续等待或被 max-age 收口 |
| InProgress 最大年龄 | `IN_PROGRESS_MAX_AGE` = 20s（> 最坏正常 dispatch 2+3+8=13s） | 转稳定失败 tombstone（按 Completed retention 管理） |
| InProgress 总量 | `IN_PROGRESS_CAPACITY` = 256 | 达上限拒绝全新 ID（`INTERNAL_SAFE_ERROR`，不接受不执行） |

### 7.2 writer ack 超时后的 fencing（§四C）

`enter_unknown_outcome_fault()`：锁存 `writer_fault`（进程内不可逆）→
强制 desired/effective/watch/shared=Stopped → `Writer/AGENT_WRITER_FAULTED`
诊断 → 返回 `AGENT_WRITER_FAULTED`（"提交结果未知，需要重启/诊断"）。
此后 `apply_capture_command`（start/resume，及 pause/stop 经状态机先行拒绝）/
`apply_settings`/`apply_system_event` 全部在副作用前被 fencing 拒绝，零
barrier/control；Writer 迟到完成不解除 fault、不允许新控制与其交错；
IPC status/diagnostics 保持在线；同 request ID 经 request cache 返回同一
稳定结果，绝不重发。

### 7.3 request cache 完成守卫（§四D）

- `RequestState::InProgress { receiver, created_at, generation }` /
  `Completed { response, at, generation }`；generation 单调递增。
- supervisor：dispatch 在嵌套 JoinHandle 中执行；成功/错误/panic/取消
  （JoinError::is_cancelled 区分文案）都写入稳定终态。
- `complete_request` 仅接受同一 generation 的 InProgress 或 Completed：
  旧任务不得覆盖新条目；同一 dispatch 的迟到真实结果允许覆盖其 tombstone。
- stale InProgress（>20s）→ tombstone（`INTERNAL_SAFE_ERROR`"原命令超时未决"），
  按 Completed TTL/容量管理；`purge_expired_at(now)` 支持测试注入未来时刻。

## 8. timeout 发生点：control 前 vs control 已接受后

- **control 前**（副作用未进 Writer）：barrier send timeout、injected ack
  timeout、inject Closed/RequestClosed、publish/健康失败——结果一律是
  **未提交**，按各路径既有语义收尾（lifecycle fail-closed、settings LKG、
  system-event 诊断），不产生 WriterControl。
- **control 已接受后**（副作用可能已提交）：Writer ack timeout——结果不是
  "未提交"而是**结果未知**（fencing + 重启/诊断语义）；Writer ack 返回错误——
  **未提交**（Writer 自证拒绝，last-known-good）；Writer ack 成功但最终
  publish 失败——**已提交**（不回滚，安全停止并明确说明）。

## 9. "未提交 / 已提交 / 结果未知" 三类结果严格区分

| 类别 | 判据 | 系统行为 | 对外错误 |
|---|---|---|---|
| 未提交 | control 未发送，或 Writer ack 明确拒绝 | 无副作用或 Writer 自证回滚；按路径语义（fail-closed / LKG / 诊断） | `INTERNAL_SAFE_ERROR` / Writer 精确码（如 `SETTINGS_CONFLICT`） |
| 已提交 | Writer ack 成功 | 边界/Settings 已入 DB，不回滚；后续步骤（watch 交付、publish）失败如实返回错误并保持已提交事实 | `INTERNAL_SAFE_ERROR`（"已提交但…"）或成功 |
| 结果未知 | Writer ack 超时（control 已被 Writer 接受） | fencing：writer_fault 锁存、Stopped、禁止再入 Writer、不重发、IPC 在线 | `AGENT_WRITER_FAULTED`（"提交结果未知，需要重启/诊断"） |

| control 入队后 Coordinator future 被 abort/panic 无阶段保护 | 新增 `AcceptedControlGuard`；control 被接受后至确定 ack 解释前，future Drop 自动锁存 unknown fault | `abort_after_control_acceptance_fences_late_side_effect`（从真实 receiver 取到 control 后 abort，迟到 ack 不解锁） |
| unknown fault 的 DTO 仍可能 Writer Healthy / Process Running，迟到 Writer 重试可清除 fault | fault 同步写入 `writer_state=Faulted`、`process_state=Faulted`；Writer busy 恢复不得覆盖已锁存 fatal 或清除 Writer 诊断 | `writer_ack_timeout_fences_all_transitions`、`late_busy_recovery_cannot_clear_latched_writer_fault` |
| PipelineHealth 只在发布 Running 瞬间检查，任务随后退出可长期虚假 Running | `PipelineHealth::with_exit_events` 在 RAII guard Drop 时发送不可丢失退出事件；`main.rs` 启动 supervisor，经 Coordinator 同一 transition lock 主动 fail-closed；正常 shutdown 先停止 supervisor | `capture_exit_is_actively_failed_closed`、`processor_exit_is_actively_failed_closed`、`writer_exit_is_actively_failed_closed`（均覆盖事件先于 supervisor poll） |
| rev2-first 分支断言写反且未被调度触发 | 拆为 rev1-first / rev2-first 两项测试，第一条先取得 barrier 后才启动第二条，显式控制锁顺序 | `concurrent_settings_rev1_first_reads_revision_under_lock`、`concurrent_settings_rev2_first_rejects_rev1_deterministically` |
| IPC × reconciler 只看最终唯一行，未证明真实重叠 | reconciler 复用同一生产循环并增加只读 attempt 观察口；测试先钉住唯一 transition lock，确认 IPC Active 与 reconciler attempt 同时存在后放行 | `ipc_reload_and_reconciler_never_duplicate_apply` |
| Capture/Writer 退出测试只靠 yield 猜测 | Capture 用 request sender capacity 恢复证明 loop 已取走请求，并断言底层 `Closed`；Writer 用 control capacity 8→7 证明真实 control 已缓冲后才 abort | `capture_loop_exit_while_barrier_blocked_returns_closed`、`writer_task_exit_during_transition_fails_closed` |

### 14.2 当前 request cache 语义（更正 §7.1/§7.3）

- `Active` 是真实后台执行记录：真实 dispatch 结束前不可由 20s max-age、600s
  TTL 或 1024 LRU 驱逐，并始终计入 256 active 上限。
- 20s 到期只给该 Active 附加客户端可见 `INTERNAL_SAFE_ERROR/结果未知`，不释放
  执行槽位，不允许同 request ID 变成 Fresh。
- 如果 unknown 已对外发布，迟到真实结果只把 Active 转为 Completed、释放 active
  槽位；缓存继续保留原 unknown，保证同一 request ID 的响应不发生失败→成功或
  失败码翻转。
- 总缓存插入后严格 `<=1024`；仅 Completed 参与 600s TTL 与 LRU 淘汰，缓存命中
  刷新 `last_accessed`。
- 原 §7.3 所述“嵌套 supervisor”“stale 转 Completed tombstone”“迟到结果覆盖
  tombstone”均已废止。

### 14.3 当前 control/ack/任务退出语义（更正 §3/§7.2/§8/§9）

```text
Barrier request reserve(2s)
  → injected ack(3s)
  → Writer control reserve(2s)
  → control accepted：AcceptedControlGuard 开始保护
  → Writer ack(8s)
```

- control permit 未取得：确定未入队，可按未提交收尾。
- control 一旦 accepted：ack Closed、ack timeout、Coordinator cancel/panic 都是结果
  未知，统一锁存 `writer_fault + writer/process Faulted + capture Stopped`。
- Capture/Processor/Writer 任一 RAII guard Drop：退出事件即使发生在 supervisor
  首次 poll 前也会排队；supervisor 经 Coordinator 串行化后主动进入同一 fatal
  状态，已发布 Running 不会长期残留。
- Writer 迟到 ack、迟到 busy 成功与后续普通数据处理均不得清除 fatal；本进程内
  start/resume/settings/system-event 保持 fencing，IPC/diagnostics 继续在线。
- 原 §3 中“Writer 退出后保持 Paused / INTERNAL_SAFE_ERROR”与 §8 中“ack Closed
  属于未提交”的描述均已废止；正确语义是 Stopped / AGENT_WRITER_FAULTED / 结果未知。
