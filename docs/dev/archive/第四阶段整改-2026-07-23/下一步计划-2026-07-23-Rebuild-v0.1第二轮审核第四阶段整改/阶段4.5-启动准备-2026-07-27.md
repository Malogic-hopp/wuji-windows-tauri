## 2. 当前生产拓扑与已确认缺口

### 2.1 可复用基础

`CaptureCoordinator` 已拥有唯一 transition lock，并预留：

```text
desired state
+ transition / fault / writer_fault
+ session_locked / system_sleeping
→ effective capture gate
```

`gate_open()` 已要求 `desired=Running` 且所有 suppression 均为 false；
`effective()` 在 desired Running 但受抑制时发布 Paused。现有系统事件提交骨架为：

```text
transition lock → freeze → Barrier injected ack → WriterControl::Lifecycle
→ Writer ack → publish/restore
```

该骨架以及 Settings/Lifecycle/SystemEvent 共用的唯一 transition lock 必须保留。

### 2.2 G5-01：只有 Lock/Sleep 进入 Coordinator

`main.rs` 当前将 Sleep/Lock 转成 `EngineEvent::SystemSleep/SessionLocked`，而
Resume/Unlock 被直接丢弃。因此预留的两个 suppression 从未在生产路径置位，系统恢复
事件也无法解除对应抑制。

### 2.3 G5-02：两个 bool 无法表达“已冻结但边界未提交”

首次 Lock/Sleep 必须先关闭采集，再可靠提交边界。如果 Barrier/control/Writer 在
提交前明确失败，采集必须继续冻结，但重复同类事件还必须能用首次事件时间重试。
单一 bool 无法区分“边界已提交”和“等待重试”，容易在重复事件时跳过必要提交。

### 2.4 G5-03：事件泵故障当前可能静默

- `start_event_pump()` 失败当前返回 `None`，不写 SharedState/Diagnostics；
- 桥接线程启动失败会直接使 Agent 启动退出；
- 事件泵线程、std channel 或 Tokio 消费任务异常结束没有统一的 fail-closed 诊断；
- 现有可由用户 Start/Resume 清除的 lifecycle `fault` 不适合表示“生命周期监控已永久丢失”。

### 2.5 G5-04：message-only window 不能证明电源广播可达

`wuji-windows/session_power.rs` 当前创建 `HWND_MESSAGE`。message-only window 不在
普通广播窗口集合中，现有“泵能创建”测试不能证明 `WM_POWERBROADCAST` 的 Suspend/
Resume 能到达。该实现不得继续被文档描述为“真实休眠链路已验证”。

## 3. 冻结的 4.5 状态模型

### 3.1 平台无关的四态输入

Coordinator 不应继续只接收无法表示 release 的 `EngineEvent`。新增或等价实现一个
Agent 内部、平台无关的输入类型：

```rust
enum SystemLifecycleEvent {
    Lock { at_utc_ms: i64 },
    Unlock { at_utc_ms: i64 },
    Sleep { at_utc_ms: i64 },
    Resume { at_utc_ms: i64 },
}
```

Windows adapter 只负责产生四态输入；状态叠加、Barrier、Writer 和发布语义只能由
唯一 Coordinator 决定。

### 3.2 每个来源独立保存活动状态与提交状态

Lock 与 Sleep 各自至少需要等价于以下状态：

```text
active: bool
boundary_at_utc_ms: Option<i64>   # 首次进入该状态的时间
boundary_committed: bool
```

硬性规则：

1. 首次 Lock/Sleep：先令对应 `active=true` 并保存首次时间，立即发布安全冻结；
   然后才注入 Barrier 和发送 Writer control。
2. Writer 成功确认后才令 `boundary_committed=true`。
3. Barrier/control/Writer 明确未提交失败：`active` 与首次时间保留，
   `boundary_committed=false`；重复同类事件必须用首次时间重试，不得写新的时间。
4. control 已接受但 ack timeout/closed/cancel：结果未知，沿用 4.3.1 的
   `writer_fault`，不得自动重试或被迟到 ack 解除。
5. `active && boundary_committed` 时重复 Lock/Sleep 幂等成功，不得重复增加 gap
   `event_count` 或重复提交边界。
6. Unlock/Resume 只清理自己的 active/pending 状态，不创建反向 Writer 边界。
7. 乱序的 Unlock/Resume 在对应来源未 active 时为幂等 no-op，可记录安全诊断，
   不得恢复或修改另一来源。

### 3.3 desired、suppression 与 effective 的关系

```text
effective Running
  iff desired == Running
  and transition/fault/writer_fault/lifecycle_monitor_fault == false
  and lock.active == false
  and sleep.active == false
  and PipelineHealth/control plane 可发布
```

- Unlock/Resume 绝不能修改 desired；Pause/Stop 后的系统恢复事件不得启动采集。
- Lock/Sleep 叠加时，release 只移除自己的 suppression；另一来源仍 active 时继续
  Paused。
- 最后一个 suppression 解除后，只有 desired Running 且健康检查通过才恢复。
- 系统事件、Settings、用户 Pause/Resume/Stop 继续由同一 transition lock 严格串行。

### 3.4 重叠 gap 语义

Lock 与 Sleep 都是可靠的进入边界；Unlock/Resume 不是数据库边界：

```text
Lock → Sleep → Resume → Unlock
  SessionLocked 边界 → SystemSleep 边界
  Resume 只清 sleep suppression
  Unlock 清最后一个 suppression
  恢复后的第一条有效 Observation 关闭当前 open gap
```

新 kind 的 Lock/Sleep 按 09 §6.7 关闭已有 open gap 并打开新 kind gap。release 不得
回写或改名当前 gap，也不得为了“对称”新增 Unlock/Resume EngineEvent。只有全部
suppression 解除后的第一条有效 Observation 才能关闭最后一个 open gap。

## 4. 冻结的失败语义

| 失败点 | 是否可能已提交 | 必须结果 |
|---|---:|---|
| Lock/Sleep 安全冻结发布失败 | 否 | 不发送 Barrier/control；锁存不可恢复故障；IPC/Diagnostics 在线 |
| Barrier send timeout/closed | 否 | 对应 suppression 保持 active；LifecyclePump 诊断；重复同类事件可按首次时间重试 |
| injected ack timeout/closed | Barrier 可能已入 FIFO | 不发送 Writer control；保持 suppression；由 pending TTL 清理；可按既有 4.3.1 协议处理重试 |
| control reserve timeout/closed | control 未入队 | 保持 suppression；边界未提交；重复事件可重试 |
| Writer 明确返回错误 | 明确未提交或按精确错误定义 | 保持 suppression；保留 Writer 精确诊断；不得恢复 Running |
| Writer ack timeout/closed/cancel | 未知 | 锁存 `writer_fault`，强制 Stopped；不得重试、不得被用户命令或迟到 ack 解除 |
| Lock/Sleep 提交成功后的最终 publish 失败 | 已提交 | 保留 DB 事实和 committed 状态；安全停止，不得回滚或伪装成功运行 |
| Unlock/Resume 最终 publish Running 失败 | 无新边界 | 不得虚假 Running；按 PipelineHealth/外部 fatal 进入安全停止 |
| 事件泵启动或运行中永久退出 | 后续事件不可知 | `LifecyclePump` 诊断 + 不可由普通 Start/Resume 清除的 `lifecycle_monitor_fault`；fail-closed，重启恢复 |

事件泵故障不得复用可由显式 capture 命令清除的普通 lifecycle `fault`。建议新增独立
`lifecycle_monitor_fault` suppression；其唯一恢复方式是 Agent 重启并成功重建事件泵。

## 5. Windows adapter 决策

4.5 默认采用以下方案，除非实施时用 Microsoft 支持文档与真实原型证明另一方案更可靠：

1. 将 `HWND_MESSAGE` 改为**不显示的顶层窗口**：parent 为 null，不设置
   `WS_VISIBLE`，保留专用消息线程与 `GetMessageW`。
2. 对该窗口继续注册 `WTSRegisterSessionNotification`，接收 Lock/Unlock。
3. 通过该顶层窗口接收 `WM_POWERBROADCAST` 的 Suspend/Resume；至少正确处理当前基线
   所需的 suspend 与 automatic resume，重复 resume 保持幂等。
4. 创建窗口、WTS 注册、消息循环异常结束、转发通道断开都必须有可观察的终态，不能
   只写 stderr 或静默退出。
5. 自动测试可验证窗口形态、消息解码与注入式事件源；不得声称这些测试等价于真实
   Windows 锁屏/休眠广播验收。

若改用 `PowerRegisterSuspendResumeNotification` 等受支持 API，必须在完成说明记录 API、
线程/回调生命周期、注销顺序、Windows 版本约束和失败闭环，并保留相同的可注入 Agent
事件源。不得同时保留两套竞争的生产电源事件路径。

## 6. 可测试的生产接线

把 `main.rs` 中的事件消费逻辑抽成可测试的单一入口，例如：

```text
Windows SessionPowerEvent
→ bounded、无静默丢弃的 bridge
→ run_session_power_events(receiver, coordinator)
→ CaptureCoordinator::apply_system_lifecycle_event
```

- 生产 adapter 与测试注入必须共用同一 consumer，不允许测试复制一套状态机。
- burst/backpressure 必须阻塞或有明确错误；不得 `try_send` 后静默丢事件。
- consumer/bridge/pump 的异常结束必须通知 Coordinator 锁存 monitor fault。
- shutdown 时的正常通道关闭需与运行中异常退出区分，避免正常退出误报故障。

## 7. 确定性测试矩阵

所有测试使用 channel/watch、显式 rendezvous、queue depth、SQLite 查询和 paused time；
不得用随机 `sleep` 猜时序。至少覆盖：

| 编号 | 场景 | 必须证明 |
|---|---|---|
| L01 | Lock→Unlock | Lock 前先冻结；边界恰好一次；Unlock 后按 desired 恢复；首条 Observation 关闭 gap |
| L02 | Sleep→Resume | 与 L01 对称，SystemSleep 边界恰好一次 |
| L03 | Lock→Sleep→Resume→Unlock | 两个进入边界有序；单独 Resume 不恢复；最后 Unlock 后才恢复 |
| L04 | Sleep→Lock→Unlock→Resume | 反向叠加同样正确，不改写最后 open gap kind |
| L05 | Pause→Lock→Unlock | desired 保持 Paused，Unlock 后不自动 Running |
| L06 | Stop→Sleep→Resume | desired 保持 Stopped，Resume 后不自动 Running |
| L07 | 重复四态事件 | 已提交的重复进入不重复写边界；重复 release 幂等 |
| L08 | Unlock/Resume 乱序 | 不清另一 suppression，不虚假恢复，不写反向边界 |
| L09 | Barrier 注入失败 | 先冻结；零 control；active/pending 保留；重复事件使用首次时间重试 |
| L10 | control send 失败 | 边界未提交；suppression 保持；修复后恰好提交一次 |
| L11 | Writer 明确失败 | DB 无新边界；保留精确诊断；采集不恢复 |
| L12 | Writer ack timeout/closed | unknown fencing；后续 Start/Settings/SystemEvent 均拒绝 |
| L13 | release 最终 publish 失败 | 不虚假 Running，watch/shared/DTO 一致安全停止 |
| L14 | Lock/Sleep × Settings/Pause 并发 | 唯一 transition lock 严格串行，无重复 Barrier/control |
| L15 | Settings 先提交后系统事件 | Lifecycle expected_revision 读取最新 applied revision，不硬编码 |
| L16 | in-flight capture 遇 Lock | 迟到样本不越过 Barrier；锁定期间真实 Capture Loop 不再产生 Observation |
| L17 | pump 启动/桥接/consumer 异常退出 | LifecyclePump 诊断和 monitor fault 生效；普通 Start/Resume 不可解除 |
| L18 | bridge burst/backpressure | 事件有序、无静默丢弃，关闭语义可证明 |
| L19 | overlap 后首条 Observation | 仅在全部 suppression 解除后出现，并关闭最后一个 open gap |
| L20 | shutdown 正常关闭事件源 | 不误报 monitor fault，不留下 Agent/线程残留 |

除 Coordinator 纯状态测试外，至少有一组真实 Capture→Processor→Writer→SQLite 拓扑测试，
证明 Lock/Sleep 边界、gap、revision、冻结和恢复效果；不得只手工构造 `EngineEvent` 与
WriterControl 代替生产接线。

Windows 层至少覆盖：消息到四态事件的纯映射、不显示顶层窗口成功创建、启动失败传播、
运行中通道关闭。真实 Lock/Sleep 仍必须在完成说明与 `migration-status.md` 中标为 Pending。
