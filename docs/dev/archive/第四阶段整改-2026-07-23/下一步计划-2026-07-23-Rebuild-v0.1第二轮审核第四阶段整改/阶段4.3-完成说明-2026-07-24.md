## 0. 第一次复审补修摘要（2026-07-24 复审结论）

复审发现 2 个 P1 与 2 个 P2，全部修复并有确定性测试：

### 复审 P1-01：Writer fatal 不得被 capture_start/resume 复活

**问题**：`mark_fatal()` 已把 `WriterState/ProcessState` 设为 Faulted、capture
watch 与 SharedState 设为 Stopped，但初版 `sync_external()` 只同步 capture
state；随后的 `capture_start` 会清除通用 fault suppression 并重新发布 Running，
可能产生 `captureState=Running + writerState=Faulted + processState=Faulted`
的假活状态。

**修复**：

- Suppression 分离建模：`fault`（lifecycle 提交失败的安全冻结，可由合法显式
  命令解除）与 `writer_fault`（Writer/Process fatal，**本进程内不可由任何
  用户命令解除**；只有 Agent 重启并成功完成启动恢复后才重建健康状态——
  重启即新建 Coordinator，自然不带该 suppression）。
- `sync_external()` 同时读取 capture state、`WriterState`、`ProcessState`；
  发现 Faulted 时锁存 `writer_fault=true`、desired/last_published 强制 Stopped。
- `capture_start`/`capture_resume` 在状态转换前检查 `writer_fault`，
  返回稳定错误 `AGENT_WRITER_FAULTED`，零副作用（无 Barrier、无
  WriterControl，desired/effective/watch/shared/DTO 全部保持 Stopped）。

### 复审 P1-02：任务或 channel 退出后不得虚假 Running

**问题**：start/resume 不经过 Barrier/WriterControl，没有验证 Capture Loop、
Processor、Writer 是否存活；`publish()` 忽略 `capture_state_tx.send()` 失败却
继续写 SharedState；`settings_tx.send()` 同样被忽略。

**修复**：

- 新增 `pipeline_health.rs`：`PipelineHealth`（capture/processor/writer_alive）
  由三个生产任务的 **RAII 守卫**维护——任务正常返回、panic、abort 都会把
  对应标志置 false（进程内不可复活）。Coordinator 持有只读句柄，
  **不允许仅凭 SharedState 推断任务存活**。
  这是第一次复审补修时的历史 Boolean 模型；第二次复审已由 §0.5 的
  `NotStarted → Alive → Dead` 状态机替代，当前实现不再使用 `*_alive` 标志。
- `publish()` 改为返回 `Result` 的唯一状态发布点：
  - capture watch 零消费者（采集任务已退出）→ 失败，不写 watch、不写 shared；
  - 发布 Running 前必须通过 `ensure_control_plane()`：`health.all_alive()` 且
    barrier/control channel 未关闭（Processor 独立退出的窗口由
    `processor_alive` 覆盖，不只依赖 channel）；
  - 使用 `send_replace` 保留最新值，但零 receiver 已显式拒绝，不用它掩盖
    任务死亡。
- 发布失败统一 `force_stopped()`：desired=Stopped、fault suppression 置位、
  watch/shared 直接写 Stopped、来源明确的诊断；shared/DTO 绝不说 Running。
- settings 成功路径：Writer ack 之后先检查 `settings_tx.receiver_count()`，
  无法交付时**不伪装完整成功**——安全停止采集、保留真实 applied revision
  （Writer 已提交，Coordinator 不改动）、返回 `INTERNAL_SAFE_ERROR` 并设置
  `Settings/INTERNAL_SAFE_ERROR` 诊断。该状态准确含义是
  **"DB 已提交但运行时消费者不可用"**：SQLite 与 SharedState.applied 一致，
  采集处于安全停止，IPC 在线可查。
- `Ok(Err(storage))` 路径不再覆盖 Writer 按 storage.code 设置的精确 Settings
  诊断（新增 `force_stopped_keep_diagnostic()` 变体）。

### 复审 P2-01：生产接线测试必须约束真实 main 接线

**问题**：初版 `production_wiring.rs` 重新实现了一套"镜像 main"的拓扑，
main 未来出现旁路时测试仍可能通过。

**修复**：新增 `control_plane.rs` 生产装配函数 `assemble()`，
**`main.rs` 与 `tests/production_wiring.rs` 调用同一个装配函数**：

- 返回唯一 `Arc<CaptureCoordinator>`；
- BarrierRequest sender 只在装配内部移交给 Coordinator，从不暴露；
- 完整 `mpsc::Sender<WriterControl>` 不暴露给任何业务调用方——
  Lifecycle/SettingsApplied 在类型上只能由 Coordinator 构造；
- Heartbeat/Checkpoint/Shutdown 改走窄通道 `MaintenanceControl`
  （`heartbeat.rs`/`maintenance.rs`/main 关闭序列全部改用）；
- `main.rs` 作用域内不再出现 `WriterControl`、`mpsc::Sender<WriterControl>`
  或 `barrier_request_tx`。

### 复审 P2-02：timeout 测试名实相符（采用方案 A）

`ipc_timeout_retry_returns_original_result_in_wiring` 重命名为
**`same_request_id_replays_original_result_in_wiring`**：它确定性地验证真实拓扑下
"同 request ID 重放原任务结果、revision 1 恰好提交一次"，不再被称为 timeout
证据。timeout 不取消副作用的确定性证据仍是
`ipc_protocol::timeout_does_not_cancel_side_effect_and_retry_returns_real_result`
（control ack 被人为推迟超过 3 秒，首次必然 timeout，重试返回原任务真实结果）。

## 0.5 第二次复审补修摘要（2026-07-24 第二次复审结论）

第二次复审发现 1 个 P1 与 3 个 P2，全部修复并有确定性测试：

### 复审二 P1：首次 poll 前 abort 的假健康窗口

**问题**：`PipelineHealth::new()` 初始为 Alive，guard 在异步任务内部第一行才
创建；JoinHandle 在首次 poll 前被 abort 时 guard 从未存在，健康标志错误
保持 true，`capture_start` 可能短暂返回 Running。

**修复**（NotStarted/Alive/Dead 状态机）：

- `PipelineHealth::new()` 三个任务一律初始 `NotStarted`（不再"初始即健康"）。
- `register_capture/processor/writer()` 以
  `compare_exchange(NotStarted → Alive)` **同步**注册——必须发生在
  `tokio::spawn` 之前；重复注册或死亡后复活一律 panic（内部不变量）。
- guard 被 move 进任务 future：正常返回、panic 展开、poll 后 abort、
  **首次 poll 前 abort**（future 销毁时连同捕获的 guard 一起 Drop）都会
  写为 `Dead`；`Dead` 不可逆。
- 三任务接线：`spawn_capture_loop` 与 `spawn_observation_processor` 在函数内
  同步注册后再 spawn；Writer 新增 `WriterTask::into_run_future()`——返回
  future 前同步注册，guard 由 future 捕获（main 与生产拓扑测试统一改用；
  `run()` 不再注册健康，仅供不接入健康模型的既有单元测试）。
- `assemble()` 刚返回但任务未注册时 `all_alive()==false`，Coordinator 拒绝
  Running；main 的接线顺序保证三个任务全部同步注册完成后才启动
  CommandServer/reconciler/session-power 控制入口。

确定性测试（`current_thread` runtime；spawn 后不 yield、立即 abort，无随机 sleep）：
`capture_abort_before_first_poll_marks_dead`、
`processor_abort_before_first_poll_marks_dead`、
`writer_abort_before_first_poll_marks_dead`、
`assemble_without_registered_tasks_rejects_start`、
`processor_abort_before_first_poll_blocks_capture_start`
（channel 全开仍拒绝，证明拒绝来自健康状态）；lib 单测覆盖
NotStarted 初始、逐一注册、guard Drop 置 Dead、重复注册 panic、Dead 不可复活。

### 复审二 P2-01：Lifecycle 最终发布失败不得静默成功

**问题**：Pause/Stop 的 Writer ack 成功后 `let _ = self.end_transition(false);`
丢弃错误；Capture Loop 在双 ack 期间退出时命令仍返回成功。

**修复**：`end_transition(false)` 失败时——生命周期边界已提交（不回滚、不
伪造未提交）、`force_stopped_keep_diagnostic()` 安全停止、返回
`INTERNAL_SAFE_ERROR`（"生命周期边界已提交但采集流水线不可用，采集已安全停止"）；
Writer 已有更精确 fatal 诊断时不覆盖（仅在无 Writer 来源诊断时补
`Writer/INTERNAL_SAFE_ERROR`）。Pause 与 Stop 同一规则。
测试：`pause_final_publish_failure_returns_error_and_safe_stops`、
`stop_final_publish_failure_returns_error_and_safe_stops`（ack 成功后关闭
capture watch receiver，断言错误码、边界已提交语义与五处状态一致）。

### 复审二 P2-02：Settings 提交后 watch 失败测试修正

`settings_watch_undeliverable_after_commit_is_not_success` 现在按真实 Writer
顺序先 `shared.set_applied_settings_revision(1)` 再发送 `Ok(1)` ack，断言
失败后 applied revision 保留为 1（不被回退为 0）。

真实 Writer 拓扑版本**不可行**，如实说明：settings watch 零消费者要求
Capture Loop 与 Processor 同时退出，但 Barrier 注入由 Capture Loop 承担——
双死亡场景会以 `RequestClosed` 在注入阶段失败（未提交语义，已有
`settings_injection_failure_keeps_last_known_good` 覆盖），"已提交但无法
交付"只在 mock harness（Writer 与 Capture Loop 分离）中可达，故保留单元级
确定性覆盖。

### 复审二 P2-03：hang/S2-06 的真实未关闭状态

删除"任务 hang 已由现有 timeout 覆盖"的错误表述（见 §8 遗留风险更正）。
如实记录：PipelineHealth 只覆盖任务退出/panic/abort；injected ack 等待无
timeout；IPC 3 秒 timeout 只结束本次客户端等待，不释放后台 transition lock；
Writer 5 秒 drain 超时仅在 injected ack 成功并发送 WriterControl 后生效。
该风险与既有 S2-06 对齐，**未关闭**，留待后续明确阶段单独处理；本轮未做
协议重构，未取消 accepted side effect，未破坏同 request ID 等待原任务的合同。

## 2. 状态字段所有权

| 状态 | 存储 | 写者 | 读者 |
|---|---|---|---|
| desired capture state | `CaptureCoordinator.state` | 仅 Coordinator（transition lock 内） | Coordinator |
| transition/fault suppression | `CaptureCoordinator.state.suppressions` | 仅 Coordinator | Coordinator（gate 计算） |
| **writer_fault suppression** | 同上 | 仅 Coordinator.sync_external（发现 Faulted 时锁存，进程内不清除） | Coordinator（start/resume 把关、gate 计算） |
| session_locked/system_sleeping | 同上（字段已建模，**4.5 才接线**） | 4.5 | Coordinator（gate 计算） |
| effective gate | 由 desired + suppressions 派生 | — | Coordinator |
| capture watch（`capture_state_tx`） | tokio watch | Coordinator.publish；**例外**：WriterTask `mark_fatal` 故障安全停止（写 Stopped） | Capture Loop |
| `SharedState.capture_state`（DTO/心跳） | SharedState | Coordinator.publish；**例外**：`mark_fatal` | IPC status_get、心跳 |
| settings watch | tokio watch | 仅 Coordinator（Writer ack 成功后、解冻前交付） | Capture Loop、Processor |
| applied settings revision | SharedState atomic | 启动时由 main 按启动对账结果初始化；运行时仅 WriterTask（DB 提交成功后） | Coordinator（锁内读取作 expected_revision）、reconciler 预检、IPC 预检 |
| capture_blocked | SharedState atomic | main（启动对账） | Coordinator（capture_start 把关） |
| PipelineHealth 三任务状态 | `PipelineHealth` 的 `AtomicU8`（NotStarted/Alive/Dead） | spawn 前同步 register 置 Alive；任务 future 销毁时 RAII guard 置 Dead（不可复活） | Coordinator（Running 发布前置条件） |

外部故障停止的并入规则：`mark_fatal` 把 watch 与 shared 同时写为 Stopped 并标记
WriterState/ProcessState Faulted；Coordinator 每次 transition 入口与结束前执行
`sync_external()`——发现 Faulted 时锁存 `writer_fault` 并强制 desired=Stopped，
否则把外部 capture state 并入 desired。`publish()` 是唯一状态发布点：
watch 与 shared 在一次成功调用中写入同一个 effective 值，发布失败时不写任何
一处并由 `force_stopped()` 统一回退 Stopped。

## 3. 失败时序

| 路径 | 失败点 | 行为 |
|---|---|---|
| start/resume | writer_fault 已锁存 | `AGENT_WRITER_FAULTED`，零副作用，全部保持 Stopped（复审 P1-01） |
| start/resume | 控制面不健康（任务死亡/channel 关闭/watch 无消费者） | `INTERNAL_SAFE_ERROR`，`force_stopped`：desired/shared/watch/DTO 全部 Stopped（复审 P1-02） |
| pause/stop | 状态机非法 / 幂等 | `CAPTURE_INVALID_STATE` / 幂等成功，无 barrier/control |
| pause/stop | 冻结发布失败（watch 无消费者） | `force_stopped`，无 barrier/control（复审 P1-02） |
| capture_start | capture_blocked | `SETTINGS_INVALID`，无 barrier/control |
| pause/stop | Barrier 注入失败 | 不发送 control（无悬挂）；fail-closed：desired=目标态、watch=shared=DTO=目标非 Running 态；`Writer/INTERNAL_SAFE_ERROR` 诊断；显式命令可解除（但管线已死亡时发布 Running 会被拒并回退 Stopped） |
| pause/stop | control 发送失败/ack 通道断 | 同上 fail-closed |
| pause/stop | Writer ack Err | Writer 已自诊断（必要时 mark_fatal）；`sync_external` 后 fail-closed，返回 ack 的稳定错误码 |
| settings | revision < applied | `SETTINGS_CONFLICT`（锁内复检），无 barrier/control |
| settings | 注入/发送/ack 断 | 不发送或不再等待；last-known-good 继续（管线存活则解冻恢复 Running，管线死亡则 `force_stopped`）；`Settings/SETTINGS_SAVED_NOT_APPLIED` 诊断；reconciler 下周期重试 |
| settings | Writer ack Err | Writer 的精确 Settings 诊断保留（Coordinator 不覆盖）；解冻恢复 Running（管线死亡则安全停止） |
| settings | ack 成功但 settings watch 无消费者 | **不伪装完整成功**：安全停止、applied revision 保留、`Settings/INTERNAL_SAFE_ERROR` 诊断、返回 `INTERNAL_SAFE_ERROR`（复审 P1-02） |
| settings | ack 成功但 Running 解冻发布失败 | 安全停止、applied revision 保留、返回错误（复审 P1-02） |
| Sleep/Lock | 注入/发送/ack 失败 | 不改变 desired；管线存活则恢复 Running，死亡则 `force_stopped`；`LifecyclePump/INTERNAL_SAFE_ERROR` 诊断；成功后清除 LifecyclePump 来源 |
| IPC | 3s timeout | 只结束等待：dispatch 在独立任务中继续执行，完成后写入 request ID 缓存；同 ID 重试等待并返回原任务结果（既有 R05 机制，未改动） |

关于"settings 失败保持安全冻结"的语义说明：settings 路径冻结的是
settings/revision/watch（last-known-good 不被半成品覆盖）；采集是否继续取决于
管线是否存活——存活则解冻恢复 Running（Writer 端旧 settings 仍确定生效），
死亡则安全停止（绝不虚假 Running）。lifecycle 路径冻结的是采集
（fail-closed），因为用户已明确要求停止采样。
