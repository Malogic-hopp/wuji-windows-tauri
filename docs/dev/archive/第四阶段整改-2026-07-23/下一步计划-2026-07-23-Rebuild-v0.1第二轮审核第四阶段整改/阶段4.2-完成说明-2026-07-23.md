### 补修中发现的引擎缺陷（附带修复）

满载测试暴露了一个真实的 ActivityEngine 误报：`last_message_epoch` 此前按
`max(共享 drop 计数器, 消息 epoch)` 更新。当 processor 在 writer lane 满载时
丢弃新样本后，仍排在队列中的旧 backlog 会被误判为"滞留旧 epoch 消息"并产生
`clock_changed` gap。修复：

- `last_message_epoch` 只跟踪已见消息的最大 epoch；
- Engine 自身在时钟异常路径 bump epoch 时同步更新 last_message_epoch
  （避免后续样本被误判为 queue drop）。

修复后全部既有 clock/queue-drop/守恒测试仍通过（全量 159 项，见 §6）。

### 复审补修（第七轮，2026-07-24）

第七轮复审针对两个安全竞态，采用审核推荐的"原生 Windows 创建 + DuplicateHandle"
方案修复，PowerShell 身份文件协议整体删除。

**为什么 PID→OpenProcess 仍存在身份错绑**：身份文件写出 PID 后、Rust
`OpenProcess(pid)` 前，原进程可能已退出且 PID 被系统复用——句柄虽不再被复用，
却已绑定到错误进程，后续可能误杀。StartTime 校验可以缓解但仍是补丁。
正确原语：进程创建后立即 `DuplicateHandle` 复制 Child 自带句柄——
句柄指向的进程对象从创建一刻起就是确定的。

**最终句柄获取方式**（`crates/wuji-windows/src/process_handle.rs`）：

- `ProcessHandle::duplicate_from_child(&Child)`：AsRawHandle + DuplicateHandle
  （DUPLICATE_SAME_ACCESS），RAII CloseHandle；
- `is_alive() -> io::Result<bool>`、`wait_exit() -> ProcessWaitOutcome{Exited|Timeout}`：
  `WAIT_FAILED` 一律返回 Err，绝不把查询失败当成"已退出"（复审 P2-01）；
- 公开 API 不再提供按 PID 的 `OpenProcess`（从身份来源中移除）。

**detached 启动时序（复审 P1-02）**：原生 `Command` +
`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`
（与生产 agent_controller 一致，09 §9.3；不继承父进程 console/句柄）→
spawn 后立即 DuplicateHandle → 登记 → 丢弃原 Child（std Child 的 Drop 不终止进程，
父句柄释放即"启动器退出"语义）。无 PowerShell、无身份文件、无 launcher 超时、
无 PID 交付竞态；故障注入点统一在 register 的复制步骤（测试可注入确定性错误，
注入后 kill + wait，无孤儿）。

**登记失败闭环**：`spawn_tracked_agent` 与 `launch_detached_tracked` 均为
创建 → 复制 → 登记成功才返回；任一步失败用仍持有的 Child 执行 kill + wait。

**身份与注销 API（复审 §六）**：`TrackedProcessKey`（guard 内单调递增）；
`untrack(key)`、`force_kill_and_wait(key, timeout)`；PID 只用于日志；
同一 PID 的新旧身份是不同 key（有测试）。

**强杀与 untrack 顺序**：terminate（存活才调用）→ terminate 失败时先
wait_exit 确认（进程可能已在终止中，不再误报）→ 句柄 Exited 才 untrack；
wait 超时/状态查询失败保留登记并报错。

**Drop 清理与目录保留规则（复审 §七）**：同连接优雅退出（hello+shutdown+willExit）
→ 句柄逐个 wait_exit → 仍存活 terminate → 再 wait；只有全部确认退出才删除
channel 目录，否则保留目录并 eprintln 诊断（不 panic、不误杀）。

**复审 P1-03（伪失败测试）处理**：删除写入 `PID|0` 的伪身份文件测试，
改为确定性故障注入：spawn/detached 两路径复制失败 → 立即 kill + wait 无残留；
detached 丢弃原 Child 后 Agent 仍在线；强杀超时保留登记后可恢复。

本轮针对第七轮实现仍未闭合的“真实父进程退出、登记失败责任、错误传播与
确定性测试”四类问题补修；没有开始 4.3。

**真实父进程退出门禁**：第七轮 `launch_detached_tracked` 只在当前测试进程内
丢弃 `Child`，只能证明原始 Child 句柄释放后 Agent 仍在线，不能证明创建 Agent
的父进程已经退出。本轮新增真实 launcher 编排：

1. 主 E2E 启动独立的 `agent_e2e` launcher 测试进程；
2. launcher 原生 detached 创建 Agent，并在自身进程中保留原始 `Child`；
3. launcher 原子写出 Agent PID 与其地址空间内的 HANDLE 数值；
4. 主 E2E 在 launcher 仍存活时调用
   `ProcessHandle::duplicate_from_remote_process(&launcher, remote_handle)`，
   通过 Windows `DuplicateHandle` 把同一进程对象的句柄复制到主 E2E；
5. 主 E2E 完成稳定 key 登记后写 ack；launcher 丢弃原 Child 并真实退出；
6. 主 E2E 先确认 launcher 已退出，再完成 Agent hello、持续落库、句柄强杀确认和
   SQLite 离线读取/`quick_check`。

该时序不以 PID 重新打开 Agent，PID 仅作日志；进程身份仍由创建时的原始句柄
跨进程复制而来。handoff 超时、内容解析失败、远程句柄复制失败会写 cancel；
launcher 收到 cancel 后用仍持有的原始 Child 执行 kill + wait 再退出，异常交付
路径不会留下无身份 Agent。

**登记失败责任闭环**：`TestAgentGuard` 新增 `emergency_children`。spawn/detached
在 DuplicateHandle/登记失败后执行有上限的 Child kill + `try_wait`；如果首次清理
没有确认退出，不再丢弃最后一个 Child，而是把它保留到 guard Drop 继续精确清理。
新增确定性故障注入覆盖“复制失败 + 首次清理失败”，并断言 Drop 后 Agent 残留 0、
确认退出后才删除 channel 目录。

**WAIT_FAILED 显式传播**：`ProcessHandle::is_alive`/`wait_exit` 保持
`io::Result`；`TestAgentGuard::is_alive`、graceful shutdown、强杀和 Drop 的句柄
查询均显式处理错误。最终复核又移除了 graceful shutdown 等待阶段残留的
`unwrap_or(false)`，状态查询失败保留 PID 与系统错误诊断，不折叠为普通超时或
“已退出”。

**确定性 timeout 覆盖**：`force_kill_timeout_keeps_tracked_then_recovers` 改用
`force_next_wait_timeout_for_tests` 注入 wait timeout 分支，不再依赖 0ms 等待与
Windows 调度竞态；失败后必须保留登记，下一次确认 Exited 后才能 untrack。

## 1. 协议时序（注入 → FIFO → control → Writer）

```text
调用方（CommandServer/reconciler/Lock-Sleep 泵/未来的 Coordinator）
  ① 生成唯一 BarrierId + expected_revision（= 接受命令时 shared.applied revision）
  ② inject_barrier：BarrierRequest{token, injected_ack} → Capture Loop
  ③ Capture Loop 将 Barrier 写入 CapturePipelineItem FIFO（与 Sample 同一队列、保序；
     容量满时阻塞等待，不丢弃）→ 写入成功后 send injected_ack Ok
     任一失败（request channel 关闭/FIFO 关闭/任务退出）→ 稳定错误，不发送 control
  ④ 收到 injected ack 后才发送 WriterControl{barrier_id, expected_revision}
  ⑤ Writer 优先消费 control：drain_to_barrier 按 ID+kind+expected_revision 三要素
     在 pending 或 FIFO 中匹配；再经 verify_engine_revision 校验 Engine 真实 revision；
     任一不符 → 错误/毒化，不提交边界
```

注入失败与 WriterControl 之间没有悬挂等待：control 只在 injected ack 之后发出；
注入失败的唯一副作用是 capture watch 已冻结（lifecycle 路径），该路径在注入失败时
立即把 watch 恢复原值。

## 2. Writer pending 规则（`PendingBarriers`，`writer_task.rs`）

- 单一 `HashMap<BarrierId, PendingState>`（Pending / Poisoned）；
- **总容量 64（pending + poisoned 合计，复审 P1-01）**：全新 ID 登记满则
  Overflow 拒绝并诊断；已有 entry 转 poisoned 原地转换不增长；
- **全局饱和降级（第三轮复审 P1-01）**：毒化不在表中的 ID 且容量满时，记录
  `saturated_until = now + TTL`；饱和期间全部新 ID 登记返回 `Saturated`
  （已有条目的 Duplicate/Conflict 原地转换不受影响），TTL 到期自动解除——
  同时满足严格容量上限与"冲突 ID 在 TTL 内不得洗白"；
- TTL 30 秒：过期条目与过期 tombstone 在 register/take 时惰性清除，饱和同时解除；
- 重复：同 ID 且 kind/revision 完全相同 → 保留首条（重传幂等），只能被消费一次；
- 冲突：同 ID 不同 kind 或不同 expected_revision → 毒化该 ID 并上报诊断；
- 毒化（复审 P2-01）：TTL 到期前不得再次登记或消费（防洗白）；
- 消费：`take_if_matches(id, kind, expected_revision)` 三要素匹配才取走；
  kind 不符 → KindConflict + 毒化；revision 不符 → RevisionConflict + 毒化；
- Engine 校验（复审 P1-01）：匹配成功后 `engine.settings_revision()` 必须等于
  expected_revision，否则拒绝并毒化；
- 普通 data 分支遇到 Barrier 一律 `register_pending`，不得跳过（含 Shutdown 的
  drain_all 路径）；Shutdown 退出时报告 pending/poisoned 分项数量与 saturated
  标志并丢弃。

## 3. 失败闭环

| 失败点 | 行为 |
|---|---|
| request channel 关闭 | `inject_barrier → RequestClosed` |
| FIFO 关闭 / Capture Loop 写入失败 | `inject_barrier → Closed`（ack 显式或中断兜底） |
| 注入失败（lifecycle） | 恢复 capture watch，不发送 control，IPC 返回稳定错误 |
| 注入失败（settings_reload/reconciler） | 不发送 control；reconciler 下周期重试 |
| 注入失败（Lock/Sleep 泵） | 不发送 control，`ErrorSource::LifecyclePump` 诊断（4.5 统一） |
| Barrier 先到 | 登记 pending，control 到达时三要素匹配消费 |
| 同 kind 不同 ID | drain 5s 超时，错误返回，不提交边界 |
| ID+kind 匹配但 revision 不符 | RevisionConflict + 毒化，拒绝应用边界 |
| Engine revision 已前进 | SETTINGS_CONFLICT + 毒化（复审 P1-01） |
| data lane 断开 | drain 立即返回稳定错误 |
| 注入后 control 超时 | 边界不提交（`timeout_does_not_commit` 类断言覆盖） |
