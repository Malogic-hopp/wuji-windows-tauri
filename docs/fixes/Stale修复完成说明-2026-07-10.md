## 改动详情

### Phase 1：前台窗口标题采集止血

**问题**：`GetWindowText` 向目标窗口线程发送同步 `WM_GETTEXT`，目标窗口挂起时 Agent 线程无限期阻塞，整个 TickAsync 循环停止，15 秒后判定 Stale。

**修复**：
- 用 `SendMessageTimeout(WM_GETTEXT, SMTO_ABORTIFHUNG, 500ms)` 替代 `GetWindowTextLength` + `GetWindowText`
- `SMTO_ABORTIFHUNG`：目标窗口挂起时立即返回，不等待超时
- 超时 `500ms`：目标正常但响应慢时的硬上限
- 固定 `StringBuilder(512)` buffer，省去 `GetWindowTextLength` 预查（从 2 次跨进程调用减为 1 次）
- 降级行为：标题为空时返回 `null`，`Capture()` 仍产生 `ProcessName = "Unknown"` 的样本，不中断主循环

### Phase 2：Tick 阶段级诊断

**问题**：看到 Stale 时只能知道"心跳过期"，无法判断卡在采集、写库、持久化还是维护操作。

**修复**：在 `AgentHealthState` 中增加 8 个诊断字段，Agent 在 `TickAsync` 执行过程中维护，每次 `PersistAsync` 成功时落盘到 `health_state.json`：
- `LastTickPhase` — 进入当前/最近阻塞调用前设置的阶段（`Capture` / `SampleInsert` / `SessionAggregation` / `Persist` / `PrivacyFilter` / `PruneData` / `ClearHistory`）
- `LastTickDurationMs` — 整个 tick 耗时
- `LastCaptureDurationMs` — 前台采集耗时
- `LastPersistDurationMs` — 状态持久化耗时
- `LastMaintenanceDurationMs` — 维护操作耗时
- `LastErrorCode` + `LastErrorMessage` — 最近错误（成功路径会清空）
- `LastSuccessUtc` — 最近一次成功完成 tick 的时间

**已知局限**：阶段和耗时数据仅在 `PersistAsync` 成功时将 `health_state.json` 落盘。如果阻塞发生在 PersistAsync 尚未被调用的阶段（例如 SQLite await 卡在 `InsertAsync` 或 `HandleSampleAsync` 内部），health_state 中看到的仍是上一个已成功持久化的阶段。因此诊断信息反映的是「最近一次成功落盘的阶段摘要」，不能保证一定是「卡住当下的真实阶段」。

### Phase 3：Diagnostics 展示

在 Diagnostics 标签页新增 "Tick Diagnostics" 卡片，直接展示：
- Last phase / Tick duration / Capture / Persist / Maintenance 耗时
- Last tick error（错误码 + 消息）

Stale 发生时，用户可切换到 Diagnostics 页参考：

- `IsRunning=false` + runtime_state 文件存在 → 进程已退出，状态文件残留（最确定）
- `LastTickPhase` 为 `Capture`、耗时正常、心跳停止 → 前台采集可能阻塞
- `LastTickPhase` 为 `SampleInsert` / `SessionAggregation`、心跳停止 → SQLite 写入可能阻塞
- `LastTickPhase` 为 `PruneData` / `ClearHistory` → 维护命令可能耗时过长
- `LastTickErrorCode` 非空 → 上一次失败的错误码，帮助判断最近异常类型

> **注意**：以上判断基于「最近一次成功落盘的阶段摘要」。若阻塞发生在 PersistAsync 之前的阶段，health_state 中看到的 Stage 可能比实际卡点滞后一个 tick。未来可考虑在进入关键阻塞调用前做独立 checkpoint 写入，实现更精确的实时卡点定位。

## 审核修复（R2）

> 审核日期：2026-07-10

### 发现

1. **高**：R1 的错误清理、`LastSuccessUtc` 设置在 privacy filter / sample captured / Paused heartbeat / Heartbeat 路径中都在 `PersistAsync` **之后**执行。`CreateHealthSnapshot()` 在 `PersistAsync` 内部调用，因此 `health_state.json` 中仍可能看到旧错误和旧时间戳。
2. **中**：`ClearHistory` 的 `_dataMaintenanceService is null` 和 `!clearResult.SqliteCleared` 分支没有设置 `_lastTickErrorCode` / `_lastTickErrorMessage`。
3. **低**：文档中「实时记录」措辞容易让人误以为数据实时可见。

### 修复

| # | 修复 | 影响文件 |
|---|------|----------|
| 1 | 在所有成功路径中，将 `_lastTickErrorCode = null`、`_lastTickErrorMessage = null`、`_lastTickSuccessUtc = DateTime.UtcNow` 移到 `PersistAsync` 调用**之前**，确保 snapshot 写入的是干净状态。`_lastPersistDurationMs` 和 `_lastTickDurationMs` 保留在 `PersistAsync` 之后（需要测量其耗时，进入下一次 snapshot）。无心跳路径（`else` 分支）也补了错误清理。 | `AgentStateMachine.cs` |
| 2 | ClearHistory 的两个非异常失败分支补上 `_lastTickErrorCode` 和 `_lastTickErrorMessage` 赋值。 | `AgentStateMachine.cs` |
| 3 | 文档「实时记录」改为「在执行过程中维护，每次 PersistAsync 成功时落盘到 health_state.json」。 | `Stale修复完成说明-2026-07-10.md` |

## 审核修复（R3）

> 审核日期：2026-07-10

### 发现

1. **中**：`PruneData completed` / `ClearHistory completed` 成功路径在 `PersistAsync` 之后才设置 `_lastMaintenanceDurationMs`，且未在落盘前清空旧 `_lastTickErrorCode` / `_lastTickErrorMessage`，可能导致 Diagnostics 显示旧错误或维护耗时滞后一轮。
2. **中**：`PruneDataUnavailable` 分支未在退出维护状态的 `PersistAsync` 前设置 `_lastTickErrorCode` / `_lastTickErrorMessage` / `_lastMaintenanceDurationMs`。
3. **中**：方案要求记录 `ControlRead` 阶段，但 `TickAsync` 读取控制文件前未设置 `_lastTickPhase = "ControlRead"`。
4. **低**：Diagnostics 中 `Last tick error` 使用水平 `StackPanel`，长错误文本可能无法按容器宽度换行。
5. **低**：`scripts/plot_app_timeline.py` 混入与 Stale 修复无关的时间线增强改动。
