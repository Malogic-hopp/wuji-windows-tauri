# Stale 根因修复与可观测性增强方案

> 日期：2026-07-10
> 目标：解决 Agent 偶发进入 `Stale` 后“看不出原因”的问题，优先消除最可能的无限期阻塞点，并补齐诊断可观测性。

## 背景

当前 `Stale` 的用户感知是：WPF 端显示 Agent 还在某种“异常运行”状态，但心跳没有继续推进，或者状态文件看起来仍然存在，用户却很难判断到底卡在哪一步。

结合现有实现，Agent 的主循环会按秒级节拍执行，且心跳写回与采样、维护命令、SQLite 写入、JSON 文件落盘都共享同一条状态机路径。只要其中某一步长时间阻塞，整个循环就会被拖住，随后 WPF 端就会把它判定为 `Stale`。

## 结论先行

本次修复建议分成两层：

1. 先把前台窗口标题采集从“无超时同步等待”改成“有边界的同步调用”，消除最危险的卡死源。
2. 同时给 Agent 主循环补一个最小诊断面板，记录“最后卡在哪一步、每一步耗时多久、最后一个错误是什么”，这样以后再看到 `Stale`，可以直接定位根因，而不是只看到一个结果。

## 问题分析

### 1. 最可能的根因：前台窗口标题采集阻塞

当前前台采样路径里，窗口标题读取使用了 `GetWindowTextLength` 和 `GetWindowText`。这类 API 会跨进程触发同步消息，如果目标窗口线程本身卡住、挂起、正在弹模态对话框，Agent 线程就可能一直等下去。

这条路径的危险点在于：

- 它位于 `TickAsync()` 的主循环里。
- 采样调用没有单独的超时保护。
- 一旦阻塞，心跳、采样、维护命令都不会继续推进。

### 2. 次级根因：SQLite 锁等待和维护命令耗时

SQLite 写锁竞争和大范围删除会让 `PruneData` / `ClearHistory` 变慢。当前连接层设置了 `busy_timeout`，所以它通常不是“无限期阻塞”，但如果再叠加采样慢、文件删除慢、或连续维护操作，整体仍可能跨过 stale 阈值。

### 3. 另一个会被误认为 stale 的场景：进程已退出但状态文件残留

WPF 端在文件回退模式下，会综合读取 runtime state、health state、进程存在性和心跳新鲜度来判断状态。若 Agent 已退出，但状态文件还残留，UI 也可能显示成 `Stale`。这类 stale 不是“卡住”，而是“最后一次运行痕迹还在”。

## 设计目标

- 不让单个前台窗口标题采集把整个 Agent 卡死。
- 不改变现有采样、会话聚合、数据清理的业务语义。
- 让 Diagnostics 能回答三个问题：
  - 最后一次心跳是什么时候写的？
  - 最后一次采样是什么时候完成的？
  - 最近一次阻塞或失败发生在哪一步？
- 让后续 stale 定位只看 Diagnostics 就能先判断大方向。

## 方案概览

### 第一部分：替换前台窗口标题采集实现

将当前的 `GetWindowTextLength` + `GetWindowText` 改为带超时的 `SendMessageTimeout`。

#### 原则

- 目标窗口正常时，尽量仍能拿到标题。
- 目标窗口挂起时，宁可丢标题，也不能拖住主循环。
- 标题采集失败时，返回 `null` 或 unknown sample，不中断整个 tick。

#### 建议行为

- `SendMessageTimeout` 使用 `WM_GETTEXT`。
- `SMTO_ABORTIFHUNG` 必须开启。
- 超时建议控制在 `300ms` 到 `1000ms` 之间。
  - 如果希望更激进地保命，优先 `300ms` 或 `500ms`。
  - 如果希望更保守地保标题，优先 `1000ms`。
- 不再依赖 `GetWindowTextLength` 预先分配长度。
- 固定 buffer 即可，标题截断比整体卡死更可接受。

#### 影响文件

- `src/QuantifiedSelf.Windows.Infrastructure/Win32/NativeMethods.cs`
- `src/QuantifiedSelf.Windows.Infrastructure/Win32/Win32ForegroundSampleProvider.cs`

### 第二部分：给主循环加“阶段级”耗时与失败诊断

仅靠“心跳过期”无法知道卡在哪一步，因此建议在 `TickAsync()` 内把主要阶段拆出来记录。

#### 建议记录的阶段

- `ControlRead`
- `Capture`
- `PrivacyFilter`
- `SampleInsert`
- `SessionAggregation`
- `Persist`
- `PruneData`
- `ClearHistory`

#### 建议记录的字段

- `last_tick_phase`
- `last_tick_duration_ms`
- `last_capture_duration_ms`
- `last_persist_duration_ms`
- `last_maintenance_duration_ms`
- `last_error_code`
- `last_error_message`
- `last_success_utc`
- `last_sample_utc`

#### 实现方式建议

- 不要一开始就引入复杂的 tracing 系统。
- 先把这些值放到 `health_state`，必要时补充 `runtime_state` 的摘要字段。
- Diagnostics 页直接读取并显示：
  - 最近一次成功 tick 距今多久
  - 最近一次采样耗时多久
  - 最近一次持久化耗时多久
  - 最近一次错误在哪个阶段发生

### 第三部分：让 Diagnostics 能直接解释 stale

Diagnostics 页面建议至少显示下面几项：

- `LastHeartbeatText`
- `LastSampleText`
- `ProcessText`
- `ActualState`
- `IsRunning`
- `IsStale`
- `LastTickPhase`
- `LastTickDuration`
- `LastErrorCode`
- `LastErrorMessage`

如果 `Stale` 发生时还能看到：

- 心跳仍在更新，但采样阶段慢 -> 更像前台采集问题
- 心跳停了，且最后阶段是 `PruneData` / `ClearHistory` -> 更像维护命令问题
- 心跳停了，且最后阶段是 `Persist` -> 更像文件 I/O 或状态写回问题
- 进程不存在但状态文件还在 -> 更像“残留状态文件”而不是挂死

## 推荐实现顺序

### Phase 1：先止血

1. 替换 `GetWindowText` 采集逻辑。
2. 保留采样失败时的降级返回。
3. 验证在卡死窗口、模态对话框、无响应程序前切换时，Agent 仍能继续更新心跳。

### Phase 2：补观测

1. 给 `TickAsync()` 各阶段加耗时统计。
2. 把结果写进 `health_state`。
3. 在 Diagnostics 页展示最近一次失败阶段。

### Phase 3：做验证

1. 用一个会阻塞 UI 线程的测试窗口验证标题采集超时。
2. 用大数据量的 `PruneData` / `ClearHistory` 验证维护阶段是否能被识别。
3. 用人工关闭 Agent 验证残留状态文件场景不会被误判成“采样卡死”。

## 验收标准

- 切到挂起窗口时，Agent 不再因为标题采集永久卡住。
- `TickAsync()` 能在合理时间内返回，不会把主循环拖死。
- Diagnostics 可以告诉用户“最后卡在什么阶段”。
- 发生 `Stale` 时，至少能区分：
  - 采样卡住
  - 维护卡住
  - 文件写回卡住
  - 进程已退出但状态文件残留

## 风险与取舍

### 1. 标题可能丢失

这是可接受取舍。比起整个 Agent 卡死，丢一次窗口标题更合理。

### 2. 超时过短会导致标题更容易拿不到

如果业务更看重稳定运行，就优先较短超时。若更看重标题完整度，就把超时调高一点，但不要回到无边界等待。

### 3. 只改采样，不补诊断，问题仍会“看不见”

这也是为什么本方案把可观测性作为第二部分，而不是只改 Win32 调用。

## 建议的最终落点

如果只允许做一个最小改动，优先级应该是：

1. `SendMessageTimeout` 替换 `GetWindowText`
2. `health_state` 增加阶段级诊断字段
3. Diagnostics 页面显示最后失败阶段

这样既能快速降低 stale 概率，也能让下一次 stale 不再是黑盒。
