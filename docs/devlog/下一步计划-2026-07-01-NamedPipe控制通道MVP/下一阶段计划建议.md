# 四、下一步建议：阶段 9「Agent 状态流订阅 / RefreshService 优化 MVP」

我建议下一阶段做：

```text
阶段 9：Agent 状态流订阅 / RefreshService 优化 MVP
```

一句话目标：

```text
让 WPF 不再主要依赖分散定时刷新来感知 Agent 状态，而是通过统一 RefreshService 和 Agent 状态流/状态推送机制，获得更及时、更稳定、更低噪声的 UI 状态更新。
```

完整路线中也一直把 Named Pipe 之后的下一步指向状态流订阅 / RefreshService 优化，而不是立刻做托盘或安装包。阶段 8 的计划文档里也把“阶段 9：Agent 状态流订阅 / RefreshService 优化”列为 Named Pipe 后最自然的下一步。

---

# 五、为什么下一步不建议直接做托盘 / 自启

托盘和开机自启看起来很诱人，但现在还差一层“状态体验地基”。

如果直接做托盘，会遇到：

```text
Agent 状态变化要怎么实时反映到托盘菜单？
Pause / Resume 后托盘状态何时更新？
Agent 崩溃后 UI 和托盘如何同时知道？
Maintenance 中菜单如何禁用？
ClearHistory 后 Paused 状态如何同步？
```

这些都依赖统一状态刷新/订阅机制。所以建议先做阶段 9，再做托盘。

# 六、阶段 9 推荐范围

## 9.1 RefreshService 集中化

当前多个 ViewModel 里都有各自刷新逻辑。下一步可以把刷新职责统一：

```text
RefreshService
    Agent status refresh
    Dashboard refresh
    Apps refresh
    Sessions refresh
    Samples refresh
    Diagnostics refresh
    Settings lightweight refresh
```

目标不是大重构，而是让刷新入口统一、可暂停、可取消、可观测。

验收：

```text
切页时只刷新当前页
Settings IsDirty 时不覆盖编辑表单
Agent 状态刷新不阻塞数据页刷新
IPC timeout 不拖慢 UI
```

## 9.2 Agent 状态流 MVP

可以有两种方案。

更稳妥的 MVP：

```text
WPF 使用 IPC GetStatus 做集中轮询
轮询间隔短一点，例如 1-2s
只刷新 Agent 状态，不刷新重数据页
```

更进一步的方案：

```text
Agent 增加 Named Pipe status stream
WPF 订阅 AgentStatusChanged
状态变化时推送 actualState / heartbeat / lastSample / command result summary
```

我建议先采用折中方案：

```text
阶段 9.1-9.3：集中轮询 GetStatus
阶段 9.4 之后再评估是否做真正 stream
```

原因是阶段 8 刚做完 request-response IPC，先不要马上引入长连接状态流，避免复杂度跳太快。

## 9.3 状态变化驱动 UI 按钮

用统一状态驱动：

```text
Start
Pause
Resume
Stop
ReloadConfig
PruneData
ClearHistory
```

确保这些按钮的可用性来自同一个 `AgentStatusSnapshot`，而不是多个 ViewModel 各自判断。

## 9.4 Diagnostics 显示刷新健康

Diagnostics 可以新增：

```text
Refresh loop status
Last refresh success
Last refresh error
Last status source: IPC / runtime_state
Refresh interval
Skipped refresh count
```

这样以后排查 UI 卡顿和状态漂移会容易很多。

# 七、阶段 9 暂时不要做什么

阶段 9 不建议做：

```text
托盘
开机自启
安装包
Windows Service
真正复杂的事件流协议
采样数据流推送
图表
导出
应用分类编辑
```

也不要把 SQLite 查询改成 IPC。
数据仍然保持：

```text
控制走 IPC
数据走 SQLite 只读
诊断走 agent_events / JSONL
```

这条边界继续保留。

# 八、阶段 9 建议拆分

建议拆成：

```text
阶段 9.1：RefreshService 现状梳理与统一接口
阶段 9.2：Agent status 集中轮询 GetStatus
阶段 9.3：ViewModel 状态派发与按钮可用性统一
阶段 9.4：当前页数据刷新与 Agent 状态刷新解耦
阶段 9.5：Diagnostics 刷新健康状态展示
阶段 9.6：断连 / 重连 / Agent 重启场景验收
阶段 9.7：长跑验证与收口
```

第一批提交建议很小：

```text
feat(refresh): introduce centralized agent status refresh service
```

只做状态刷新集中化，不碰页面布局、不做托盘。

# 九、阶段 9 验收标准建议

完成后至少满足：

```text
1. build 0 warning / 0 error
2. test 全部通过
3. Agent 状态刷新集中到单一服务或单一协调器
4. IPC GetStatus 成功时 UI 状态及时更新
5. IPC 不可用时 fallback 到 runtime_state / health_state
6. Pause / Resume / Stop 后按钮状态不会漂移
7. Maintenance 中控制按钮和清理按钮禁用
8. Settings IsDirty 时不会被刷新覆盖
9. 当前页数据刷新和 Agent 状态刷新互不阻塞
10. Agent 重启后 IPC 状态能恢复
11. Diagnostics 能显示刷新健康状态
12. 长跑 30 分钟无 Stale 误判、无 UI 卡顿、无状态漂移
```
