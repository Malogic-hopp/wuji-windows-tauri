## requestId 防重

- ProcessedRequestCache: capacity=100, ttl=10min, 纯内存不落盘
- IPC 路径：同一 requestId 在 ttl 内重复命中返回 DuplicateRequest errorCode
- WPF fallback 也使用同一 requestId 写入 agent_control.json，Agent 侧 file 路径也能被 ProcessCommandAsync 内的现有逻辑处理

## Stop 特殊语义

- IPC Stop 发送后不等待 response（pipe 可能因 Agent 退出而 broken）
- 进入进程退出轮询，进程消失即视为成功
- IPC 不可用则 fallback 到 agent_control.json → 轮询 → kill

## 第一次审核修复（2026-07-01）

审核发现 3 个问题，均已修复（build 0/0, test 180/180）：

1. fallback 文件写入时未复用 IPC requestId —— IssueCommandAsync 新增 `overrideRequestId` 参数；IPC 超时后不 fallback（直接返回 IpcTimeout），IPC 不可用时 file fallback 使用同一个 ipc-* requestId；新增测试验证 fallback 文件 requestId 以 `ipc-` 前缀

2. Stop IPC pipe broken 后可能遗留 stale agent_control.json —— AgentProcessService.StopAgentGracefullyAsync：IPC 发送失败后先检查 Agent 进程是否已退出，已退出直接返回成功不写文件；仍在运行才写 file fallback

3. Stop 的 WaitForCompletion=false 未真正生效 —— IPC Stop 改为 Task.Run fire-and-forget：发送后立即进入退出轮询，不等待 IPC response；pipe broken 在后台任务中安静 swallow
