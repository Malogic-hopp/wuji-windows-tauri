# 我认为写得好的地方

## 1. 加了 `IStartupRegistry`，测试边界正确

你要求注册表读写通过：

```text
IStartupRegistry
```

生产实现才使用：

```text
Microsoft.Win32.Registry.CurrentUser
```

测试使用 fake registry。这个设计很重要，可以避免单元测试真实写注册表，也便于模拟读写失败、mismatch、missing value 等状态。

---

## 2. `StartupCommandBuilder` 独立出来是对的

把这些逻辑集中在一个 builder 里是合理的：

```text
当前 App exe 路径解析
Run Key command 构建
引号处理
--from-autostart / --start-hidden 参数追加
command 解析与规范化比较
dotnet.exe / dll / 空路径 / 非 WUJI App exe 拒绝注册
```

如果这些逻辑散落在 `StartupRegistrationService` 里，后续很难测试，也容易把错误路径写进 Run Key。

---

## 3. Mismatch / Unsupported 状态设计比较稳

计划里把状态拆成：

```text
Disabled
Enabled
Mismatch
Error
UnsupportedInCurrentLaunchMode
```

这比简单 bool 更好。

尤其是 `UnsupportedInCurrentLaunchMode` 很有必要。开发期如果当前入口是 `dotnet.exe` 或 `.dll`，不应该硬写 Run Key，否则会注册错误启动命令。

---

# 建议补强 1：明确 `RegisterAsync / UnregisterAsync / GetStatusAsync` 是否真异步

这几个方法名字是 `Async`，但注册表 API 本身通常是同步的。建议补一句：

```text
RegisterAsync / UnregisterAsync / GetStatusAsync 可以返回 Task.FromResult / Task.CompletedTask；不要为了“异步”强行 Task.Run 包注册表读写，除非现有项目已有统一模式。
```

原因是阶段 11.2 没必要引入线程切换复杂度。后续 Settings 调用时用 async 接口即可。

---

# 建议补强 2：明确 registry key 打开失败时的行为

生产实现需要打开：

```text
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

建议加一句：

```text
SetValue 时如果 Run 子键不存在，应创建当前用户 Run 子键；ReadValue / DeleteValue 遇到子键不存在时按 Disabled / Success 处理，不视为 Error。
```

否则如果测试或极端环境中 Run key 不存在，行为可能不一致。

---

# 建议补强 3：`DeleteValue` 不存在时不要抛异常

你已经写了 Unregister 幂等，但建议对 `IStartupRegistry.DeleteValue` 再明确：

```text
DeleteValue(name) 删除不存在的 value 时不应抛异常，或由 StartupRegistrationService 捕获并视为成功。
```

这样 Unregister 幂等更稳。

---

# 建议补强 4：command 解析要明确“缺参数”和“路径不匹配”都算 Mismatch

你已经写了 Mismatch，但建议明确判断：

```text
WUJI value 存在，但缺少 --from-autostart 或 --start-hidden，状态为 Mismatch。
WUJI value 存在，但 exe 路径不是当前 App，状态为 Mismatch。
WUJI value 存在，但 command 无法解析，状态为 Mismatch 或 Error；建议 MVP 归为 Mismatch，并给安全文案 Needs repair。
```

这样后续 Settings 可以用“Needs repair”修复，而不是把外部手改的命令都当成 Error。

---

# 建议补强 5：路径比较要分清“构建失败”和“已注册命令不匹配”

这里容易混：

```text
当前 App 路径无效 → UnsupportedInCurrentLaunchMode
已注册 command 路径不匹配 → Mismatch
```

建议加一句：

```text
UnsupportedInCurrentLaunchMode 只表示当前运行入口无法构建有效自启命令；已有 Run Key 与当前 App 不匹配时应返回 Mismatch，而不是 Unsupported。
```

这样状态语义会更清楚。

---

# 建议补强 6：错误脱敏测试可以更具体

你已经要求错误文案安全。建议加几条断言：

```text
安全错误文案不得包含：
C:\
/Users/
\Users\
S-1-5-
HKCU\Software
System.UnauthorizedAccessException
stack trace
完整 command
```

不过注意：如果你的测试在 Windows 上，路径格式主要是 `C:\` 和 `\Users\`；如果在 WSL/Linux 测试，路径可以按字符串 fake 模拟。

---

# 建议补强 7：`StartupCommandBuilder_UsesCurrentAppExePath` 测试不要依赖真实运行入口

这个测试名可以保留，但实现上不要真的依赖当前 testhost 路径。建议补一句：

```text
StartupCommandBuilder 测试应支持注入当前进程路径 provider，避免测试依赖 testhost.exe / dotnet.exe 的真实运行入口。
```

否则测试环境下当前进程很可能是 `testhost.exe` 或 `dotnet.exe`，导致不稳定。

最好是：

```text
IProcessPathProvider
    string? GetProcessPath()
```

或者构造函数传入 `Func<string?> getProcessPath`。

---

# 建议补强 8：`IStartupRegistry` 生产实现命名可以提前明确

建议新增生产实现文件：

```text
RegistryStartupRegistry.cs
```

或：

```text
WindowsStartupRegistry.cs
```

并明确：

```text
IStartupRegistry 是接口；
RegistryStartupRegistry 是 Microsoft.Win32.Registry.CurrentUser 实现。
```

这样避免 agent 只写了接口和 service，却漏掉生产实现。
