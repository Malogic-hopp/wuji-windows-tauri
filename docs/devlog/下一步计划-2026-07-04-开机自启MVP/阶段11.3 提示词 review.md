# 总体评价

这份提示词已经比较成熟。

它抓住了阶段 11.3 的核心问题：

```text
StartAppOnWindowsLogin 是 WPF App 登录自启开关；
AutoStartAgentWhenAppStarts 是 App 启动后是否自动启动 Agent；
StartupRegistrationStatus 是 OS 真实注册状态；
Settings UI 里的开关值是用户草稿。
```

这几个概念分清楚了，阶段 11 后面就不容易乱。

# 我认为写得好的地方

## 1. 保存顺序写得正确

你要求：

```text
开启 StartAppOnWindowsLogin：
    先 RegisterAsync
    成功后再保存 AppSettings=true
    失败时不宣称启用成功

关闭 StartAppOnWindowsLogin：
    先 UnregisterAsync
    成功后再保存 AppSettings=false
    失败时不宣称禁用成功
```

这是正确的。否则很容易出现 UI / AppSettings 显示已启用，但 HKCU Run Key 实际没有写成功的“假启用”。

---

## 2. Dirty 规则写得比较稳

你明确要求：

```text
Settings IsDirty=true 时：
    可以更新只读 StartupRegistrationStatusText
    不得覆盖 StartAppOnWindowsLogin 草稿
    不得触发注册表写入或删除
```

这个很重要。Settings 页面正在编辑时，后台状态刷新只能更新只读状态，不能改用户草稿，也不能偷偷写注册表。

---

## 3. 没有越界到 11.4 / 11.5

提示词明确禁止：

```text
不实现自启启动到托盘
不做 Diagnostics 自启状态展示
不改 App 启动流程
不改托盘命令
不改 Agent 命令链路
```

边界是清楚的。11.3 只负责 Settings 接入和保存同步。

# 建议补强 1：明确 “Mismatch + 保存” 的修复语义

现在提示词说 mismatch 时显示 Needs repair / Mismatch，但建议补一句：当用户在 Settings 中开启自启并保存时，如果当前 OS 状态是 Mismatch，应当通过 `RegisterAsync()` 重写为正确 command，而不是只保存 AppSettings。

可追加：

```text
如果 StartupRegistrationStatus 为 Mismatch，且用户保存 StartAppOnWindowsLogin=true，应调用 RegisterAsync() 修复为当前 App 的正确 Run Key command；修复成功后再保存 AppSettings=true。
```

这能让 Settings 具备“修复自启注册”的能力。

---

# 建议补强 2：明确 “AppSettings=true 但 OS Disabled” 的 UI 处理

你已经写了“不静默改 UI 草稿”。建议更具体：

```text
加载 Settings 时：
    StartAppOnWindowsLogin 草稿值来自 AppSettings；
    StartupRegistrationStatusText 来自 OS 状态；
    如果 AppSettings=true 但 OS Disabled/Mismatch，应显示警告状态，但不要自动把草稿改成 false。
```

这样用户看到的是：

```text
开关：开启
状态：Needs repair / Not registered
```

然后用户保存时可以修复注册表。

---

# 建议补强 3：注册失败后草稿值要怎么处理

保存失败时有两个选择：保持用户草稿为 true，提示失败；或回滚到保存前值。两种都可以，但要明确，否则 agent 可能实现得不一致。

我建议 MVP 用这个语义：

```text
注册失败时，不保存 AppSettings；可以保留用户草稿值和 IsDirty=true，并显示安全错误，让用户可以重试或取消。
```

补充：

```text
RegisterAsync / UnregisterAsync 失败时，不应把 IsDirty 清为 false；SaveStatusText 显示安全失败原因。
```

---

# 建议补强 4：避免 SettingsViewModel 直接依赖具体实现

提示词说依赖 `StartupRegistrationService`，可以接受。但为了测试和后续维护，建议更抽象一些：

```text
SettingsViewModel 优先依赖 IStartupRegistrationService 或等价接口；如果当前阶段没有接口，也至少通过 fake service 易于单元测试，不要在测试中写真实注册表。
```

这样测试 fake 更自然。

---

# 建议补强 5：Settings UI 文案要避免用户混淆

计划中说两个开关文案必须明确区分。建议直接给 agent 文案建议：

```text
Start WUJI when Windows starts
说明：Launches the WUJI app after you sign in. The window can be shown from the tray.

Start Agent when WUJI starts
说明：Starts background collection when the WUJI app opens.
```

如果 UI 是中文，则：

```text
登录 Windows 后启动 WUJI
说明：登录后自动启动 WUJI App，之后可从托盘打开窗口。

WUJI 启动后自动启动 Agent
说明：WUJI App 启动后自动开始后台采集。
```

这样不容易把“App 自启”和“Agent 自启”混在一起。

---

# 建议补强 6：状态文本只读，不参与 Dirty

`StartupRegistrationStatusText` 是 OS 状态，不是用户设置。建议补一句：

```text
StartupRegistrationStatusText 更新不应设置 Settings IsDirty=true。
```

否则状态刷新会让 Settings 页面无故变 dirty。

---

# 建议补强 7：保存 AutoStartAgentWhenAppStarts 不应误触注册表

你已经有相关测试建议。建议再明确：

```text
如果用户只修改 AutoStartAgentWhenAppStarts，而 StartAppOnWindowsLogin 未变，不应调用 RegisterAsync / UnregisterAsync。
```

这能防止每次保存 Settings 都重写注册表。
